# Дневник еды: черновик правки vs фоновое обновление данных

Парный документ: `megaapp-back/plans/17-food-diary-draft-vs-background-refresh-race.implementation-plan.md` (по итогам анализа — backend-изменений в этом раунде не требует, см. пояснение там же).

Контекст: продолжение разбора, начатого багом «проекция % отката после быстрого редактирования». Отдельная тема от `15-sync-architecture-refactor` / `16-sync-engine-and-reload-resilience` — та пара закрыла гонку **между сабмитом и подтверждением с сервера** (`pendingDiaryEntryIds` + `mergeServerDiaryResponse`). Этот план закрывает гонку **до сабмита**, пока пользователь ещё просто печатает в форме — она была вне охвата 15/16 и в них не упоминается.

## Что делаем и зачем

Триггер: в форме правки записи дневника открыт weight-инпут, пользователь вводит число, счётчик проекции % мгновенно обновляется — и через ~секунду откатывается на исходное значение сам, без участия пользователя.

**Уточнение по итогам более глубокого разбора (важно, меняет расстановку приоритетов из предыдущего обсуждения):** источник отката — не конкретно WS-триггер `SYNC_STATUS`, как казалось на первый взгляд. `FoodScreen.ngOnInit` **безусловно** дёргает полный перезапрос данных дневника при каждом заходе на экран еды (`food-screen.ts:21`), независимо от WebSocket. `SYNC_STATUS`-триггер (`food-diary.service.ts`, `handleSyncStatus`) — это **второй**, тоже безусловный источник того же полного перезапроса, срабатывающий при каждом переподключении к сокету (в том числе сразу после захода на экран). Оба источника существуют независимо и оба ничем не защищены от гонки с открытой формой правки. Значит сужение только одного из них (например, только `SYNC_STATUS`) бага не закрыло бы — второй источник (`FoodScreen.ngOnInit`) продолжил бы порождать ту же гонку при каждом обычном заходе на экран. Настоящий фикс должен быть в точке, которая одинаково защищает от **любого** источника фонового перезапроса, а не в конкретном триггере.

Второе, отдельно найденное при разборе: у формы **добавления** новой записи (`diary-entry-add-form.ts`) — тот же класс бага, независимая копия. Реакция на изменение итогов дня явно пересчитывает проекцию с введённым весом, принудительно подставленным как `0`, а не с тем, что реально в данный момент напечатано в поле. Раньше это не было замечено как проявление того же дефекта — сам баг-репорт был про форму правки существующей записи, форма добавления не проверялась целенаправленно.

**Жёсткое ограничение (как и в 15/16):** пользовательский контракт по сабмиту/сохранению/уведомлениям не меняется. Меняется только устойчивость счётчика-превью к фоновым обновлениям, пока форма открыта и не сабмитнута.

## Текущая реализация (обзор)

- **Источники фонового перезапроса данных дневника** (оба безусловны, ничем не связаны друг с другом):
  1. `FoodScreen.ngOnInit` → `FoodDiaryService.loadAllFoodData()` — при каждом заходе на экран еды.
  2. `FoodDiaryService.handleSyncStatus` (реакция на WS-сообщение `SYNC_STATUS`) → тот же `loadAllFoodData()` — при каждом подключении/переподключении сокета. Сравнение с локальной меткой `lastSyncTs` не спасает: `lastSyncTs` — поле в памяти, обнуляется при каждой перезагрузке страницы, поэтому сравнение с меткой сервера (почти всегда > 0 для существующего пользователя) проходит и триггерит перезапрос практически всегда.
  - Оба в итоге дают новый объект `diaryRaw$$` → новый объект `diary$$()[...].food[...]` для КАЖДОЙ записи дня, включая те, что реально не менялись.
- **Форма правки** (`diary-entry-edit-form.ts`): при получении нового объекта записи через `@Input` (`ngOnChanges`) безусловно перезаписывает и базовый вес записи (законно — это и есть источник истины с сервера), и **финальный вес из черновика пользователя** (`foodWeightFinal` — то, что должно уйти в запрос при сабмите). Второе стирает несохранённый ввод, если он есть. Проекция % пересчитывается императивно — явным вызовом одной и той же функции из шести разных мест (`ngOnChanges`, три обработчика ввода/сброса полей, эффект на изменение итогов дня, сброс формы) — не как единое реактивное значение.
- **Форма добавления** (`diary-entry-add-form.ts`): та же императивная функция пересчёта проекции, отдельная копия с теми же переменными и той же формулой. При изменении итогов дня (эффект) пересчитывает с весом `0` вместо текущего значения поля — тот же класс бага, другой механизм срабатывания.
- **Существующая защита от гонки** (`pendingDiaryEntryIds` + `mergeServerDiaryResponse`, сделана в `15`) — защищает только окно «сабмит отправлен → ответ сервера получен». До сабмита, пока пользователь просто печатает, id записи ещё не попал в `pendingDiaryEntryIds` — защиты нет.
- Единственный законный момент, когда черновик формы правки должен обнуляться — закрытие аккордеона записи (`food-diary.ts:270-275`, `FoodDiaryService.resetDiaryEntryForm`), которое происходит и при ручном сворачивании, и при успешном сабмите (`onServerSuccessfullEditResponse` → `closeAllAccordions()`). Других мест, где черновик должен стираться, в текущем поведении нет.

## Ключевые архитектурные проблемы

1. Проекция % — по сути производное (вычисляемое) значение, реализованное как императивно мутируемое поле с ручным пересчётом в шести местах. Такая форма кода систематически порождает баги «забыли пересчитать/забыли не затереть» — этот баг ровно такой, и он не единственный (см. форму добавления).
2. Нет разделения между «базовые данные записи, которые правомерно обновляются фоном» и «черновик пользователя, который может обновить только сам пользователь». Оба сейчас лежат в одних и тех же переменных.
3. Формула проекции % продублирована дословно между формой правки и формой добавления — уже сейчас разошлась в надёжности (в одной от бага защищена лучше чем в другой, хотя обе одинаково уязвимы).
4. Два независимых безусловных источника полного перезапроса данных (заход на экран + переподключение сокета) не скоординированы — но это, как выяснилось, не корень бага, а лишь то, что делает окно гонки шире и чаще. Сама гонка живёт в форме, а не в источниках.

## Направление рефакторинга

### Обязательная часть (закрывает баг, поведение не меняется — кроме исчезновения самого дефекта)

- **Развести «базовые данные» и «черновик пользователя» в обеих формах.** Базовый вес записи (или 0 для новой) и текущие итоги дня — источники истины, которые правомерно обновляются фоном в любой момент. Черновик — то, что пользователь ввёл в поле прямо сейчас, — меняется только тремя действиями: ввод, явный сброс поля, сабмит/закрытие формы. Фоновое обновление базовых данных никогда не трогает черновик.
- **Проекция % — единое вычисляемое значение**, зависящее только от текущего черновика и текущих базовых данных, без промежуточного мутируемого поля и без явных вызовов пересчёта по всем точкам входа. Пересчитывается сам собой при изменении любого из входов — забыть вызвать его после нового обработчика становится невозможно в принципе, а не «нужно не забыть».
- **Формула проекции % — одна реализация**, используется обеими формами (правка и добавление) вместо двух независимых копий.
- Итог для обеих форм: фоновое обновление данных дневника (от любого из двух источников, сейчас и в будущем) может обновить то, от чего считается процент, но никогда не обнуляет и не подменяет то, что пользователь реально ввёл и ещё не подтвердил.

### Пограничный случай — решение принято (2026-08-02)

- **Запись правится параллельно с другого устройства, пока на этом открыта форма правки с непустым черновиком.** Выбран вариант (а): молча пересчитать проекцию от нового базового веса, ничего не показывая пользователю — черновик применяется «поверх» уже изменённого веса при сабмите. Согласуется с тем, что уже реализовано для окна «после сабмита» (`pendingDiaryEntryIds`/`mergeServerDiaryResponse` — там тоже нет визуального конфликт-UI). Реализовано этим же изменением — отдельной ветки логики не потребовалось: базовый вес (`foodWeightInitial$$`) обновляется в `ngOnChanges` безусловно и всегда, черновик читается отдельными сигналами и в пересчёт базового веса не входит.

### Рассмотрено и сознательно не берём в этот раунд

- **Сужение источников фонового перезапроса** (сделать `SYNC_STATUS`/заход на экран не безусловными, а по факту реальной устаревшести локальных данных). После обязательной части это перестаёт быть нужным для закрытия бага — гонка закрывается в форме, независимо от частоты фоновых перезапросов. Останется отдельной, самостоятельной темой (сетевой трафик/избыточность двух дублирующих друг друга безусловных источников) — не смешивать с этим планом, если понадобится — заводить отдельным документом.
- **Обобщение шести почти одинаковых optimistic-write блоков в `FoodDiaryService`** (create/edit/delete/deleteDay/restoreDay/bodyWeight) в один параметризованный хелпер. Реальный дубляж есть, но форма отличается по домену на каждую операцию (что именно откатывать, как считать дельту) — общий хелпер рискует получиться более сложным для чтения, чем шесть прямых блоков сейчас. Не связано с этим багом. Не включено.

## Область охвата

- Только фронтенд, только дневник еды: форма правки записи + форма добавления записи.
- Не трогает: деньги, настройки, каталог еды, статистику/график, `SyncEngineService`, WS-протокол, бэкенд.

## Не входит в этот план

- Сужение частоты полного перезапроса (см. «рассмотрено и не берём» выше).
- Обобщение optimistic-write блоков `FoodDiaryService` (см. там же).
- Каталог еды на `SyncEngineService`, именованный тип вместо позиционного тюпла `Stats` — отдельные, более крупные темы, зафиксированы как идеи на будущее в парном бэкенд-документе, не начинаются сейчас.

## Затронутые флоу

| Флоу | Сейчас | После рефакторинга |
|---|---|---|
| Открыть форму правки существующей записи | Базовый вес и черновик инициализируются с сервера | Не меняется |
| Печатать вес/дельту в форме правки, фоновый перезапрос данных **не** приходит | Проекция % считается от введённого | Не меняется |
| Печатать вес/дельту в форме правки, фоновый перезапрос **приходит** (любой из двух источников) | **Баг**: проекция откатывается к исходному % | **Исправлено**: проекция остаётся от введённого черновика |
| То же самое в форме добавления новой записи | **Тот же баг**, независимая копия (проекция откатывается к приросту 0) | **Исправлено**, тем же способом |
| Сабмит формы (успех) | Уходит значение, которое видит пользователь; проекция гаснет вместе с закрытием формы | Не меняется |
| Сабмит формы (сеть недоступна / ошибка) | Существующий откат/уведомление `SyncEngineService`, не связан с этим планом | Не меняется |
| Ручное сворачивание аккордеона записи с непустым черновиком | Черновик сбрасывается (`resetDiaryEntryForm`) | Не меняется |
| **Правка той же записи с другого устройства, пока форма открыта с непустым черновиком** | Сейчас: базовый вес и черновик оба безусловно перезатираются пришедшим значением — черновик теряется незаметно для пользователя | **Требует решения** (см. «Направление рефакторинга» выше) — по умолчанию предлагается: базовый вес обновляется, черновик остаётся, пересчёт от нового базового — но это предложение, не факт |
| Гонка «сабмит отправлен → ответ сервера ещё не пришёл» | Защищена `pendingDiaryEntryIds`/`mergeServerDiaryResponse` (план `15`) | Не меняется, эта защита не трогается |

## Чеклист

- ✅ Развели базовые данные записи и черновик пользователя в форме правки — черновик меняется только вводом/сбросом/сабмитом, никогда фоновым обновлением.
- ✅ То же самое в форме добавления — включая эффект на изменение итогов дня, который раньше пересчитывал с зашитым нулём вместо текущего значения поля.
- ✅ Проекция % — одна реализация формулы (`projectDaysConsumedPercent`, `shared/utils.ts`) на обе формы вместо двух копий, вычисляемая как `computed()`-сигнал, а не через явные вызовы функции пересчёта.
- ✅ Решение пользователя по пограничному случаю — вариант (а), зафиксировано и реализовано (см. выше).
- ✅ `tsc --noEmit` чист после изменений.
- ⭕ Ручная проверка сценария из бага (быстрый рефреш страницы → быстрый ввод веса) — по правилу пользователя browser-tools не используются; проверка руками пользователем после реализации.
