# Каталог еды на стандарт operationId + SyncEngineService

Парный документ: `megaapp-back/plans/18-food-catalogue-operation-id.implementation-plan.md`.

Решение пользователя (2026-08-02): каталог переходит на общий движок синка **полноценно**, не половинчато. Раз для этого движку не хватает умения передавать содержательную ошибку и не тупить на заведомо неретраибельных отказах — это дорабатывается здесь и сейчас, а не откладывается. Объём правки — вторичен, первична архитектурная правильность.

## Что делаем и зачем

Две связанные задачи одним заходом:
1. **`SyncEngineService` — научить отличать «стоит повторить» от «это финальный отказ сервера»** и передавать содержимое отказа вызывающему коду. Без этого перевод каталога на движок либо теряет три конкретных сообщения об ошибке в форме, либо заставляет пользователя ждать ~6 секунд бессмысленных автоповторов перед показом ошибки, которая в принципе не могла исправиться повтором.
2. **Каталог еды (сохранить/удалить продукт) переезжает на `SyncEngineService`**, режим non-optimistic — получает то же самое: ретраи, `operationId`, персистентность незавершённой операции при перезагрузке страницы, — что уже есть у дневника и денег.

## Текущая реализация (обзор)

### `SyncEngineService` (`sync-engine.service.ts`)

- Единая последовательная очередь, каждая операция — `optimistic` (state меняется до постановки в очередь, откат по неудаче) или `non-optimistic` (state меняется только на успехе).
- На любую неудачу — **одинаковая** реакция: `retryCount++`, если меньше `BACKGROUND_SYNC_RETRIES_MAX` (3) — подождать `1000 * retryCount` мс и повторить; иначе — сдаться. Итого до трёх попыток с нарастающей паузой (1с, 2с, 3с — до ~6с суммарно) на **любую** ошибку, включая те, что заведомо не изменятся от повтора (сервер отверг данные — 400/404/409 и т.п.).
- `rollbackCallback`/`errorCallback` — оба объявлены как `() => void`, без параметров. Движок ловит ошибку (`catch (error)`), но никуда её не передаёт — только логирует в консоль и показывает общий текст `feedback.errorMessage`, один и тот же для любой причины отказа.
- Используется в 12 местах (6 — `food-diary.service.ts`, 5 — `money.service.ts`, 1 — `settings.service.ts`) — везде `rollbackCallback` синхронно откатывает локальный state и шлёт булев результат (`requestResult$.next({result: false})` и т.п.), ни один вызывающий код сегодня не смотрит на причину отказа.

### Каталог (`food-catalogue.service.ts`, `catalogue-entry-edit-form.ts`)

`saveProduct`/`deleteProduct` — прямые вызовы `HttpClient`, `await` на них в форме, форма разбирает тело ответа сервера и показывает одно из трёх конкретных сообщений (уже занято имя / используется в дневнике / не найдено) — см. `18` в бэкенд-документе.

## Направление

### 1. Классификация ошибок в `SyncEngineService` — retryable vs terminal

Правило (по HTTP-статусу пойманной ошибки, `HttpErrorResponse`/сетевой сбой/таймаут):
- **Retryable** (повторяем как сейчас): статус `0` (обрыв связи/DNS/CORS — соединения не было), таймаут (`TimeoutError` от `timeout()`), `429` (rate limit — есть смысл переждать), любой `5xx` (проблема на сервере, может пройти сама).
- **Terminal** (сдаёмся сразу, без ожидания): любой другой `4xx` — сервер осмысленно ответил и отверг именно эти данные, с тем же телом запроса результат не изменится (тот же принцип, на котором уже стоит идемпотентность из плана `15`).
- **Неопознанная форма ошибки** (что-то, что не `HttpErrorResponse` и не `TimeoutError`) — по умолчанию retryable, чтобы не потерять сегодняшнюю осторожность на случай непредвиденного.

Для terminal-ошибки цикл ретраев в `runOperation` завершается на первой же попытке — без `sleep`, без наращивания `retryCount` относительно лимита, сразу в ветку «сдаться».

### 2. Нормализованная ошибка вместо «молчания»

Новый тип (простой, минимальный — не оборачиваем Angular-специфичный `HttpErrorResponse` целиком, чтобы вызывающий код не зависел от деталей HTTP-клиента):
- `status: number` (0 — сеть/таймаут/неопознанное);
- `body: unknown` (распарсенное тело ответа сервера, если было — то самое `{ result: false, error: "..." }`, которое сегодня форма каталога уже разбирает вручную из `HttpErrorResponse.error`).

`rollbackCallback`/`errorCallback` расширяются до `(error: SyncOperationError) => void`. Это **обратно совместимо** для всех 12 существующих мест без единой правки в них: в TypeScript функция с меньшим числом объявленных параметров (сегодняшние `() => {...}`) остаётся валидной там, где ожидается функция с параметром — существующий код продолжает их просто не читать. Никто из дневника/денег/настроек ничего не обязан менять.

### 3. Побочный положительный эффект — не только ради каталога

Терминальные (не сетевые) отказы у дневника и денег — например, «запись не найдена» при правке дневника или отказ валидации счёта/категории у денег (см. бэкенд, `ensureTransactionAccount`/`ensureTransactionCategory`) — сегодня тоже проходят все три бессмысленных повтора перед тем, как показать ошибку. После рефакторинга — эти отказы (редкие, но существующие) будут показываться пользователю мгновенно вместо ~6 секунд впустую. Поведение улучшается и там, никто не проигрывает.

### 4. Каталог переезжает на движок — закрывает открытый вопрос из предыдущей версии этого плана

- `saveProduct`/`deleteProduct` — `SyncOperationMode.NonOptimistic`, без `feedback` (форма показывает результат сама, не нужен общий тост поверх). Внутри метода — `applyCallback`/`errorCallback` движка оборачиваются в `new Promise((resolve, reject) => ...)`, поэтому наружу метод остаётся тем же `Promise<CatalogueEntry>`/`Promise<void>`, каким был. Это проще, чем изначально описанный переход на «сырые» колбэки: `catalogue-entry-edit-form.ts` не трогается структурно вообще — `await`/`try/catch` в форме остаются как есть, меняется только то, откуда читается тело ошибки (`error.body` вместо `HttpErrorResponse.error`).
- Идемпотентность на бэкенде (задача из парного документа) — обязательная предпосылка, без неё `operationId`, который теперь шлёт движок, некому проверять.

## Область охвата

- `sync-engine.service.ts` — классификация ошибок, нормализованный тип, изменение сигнатур колбэков.
- `food-catalogue.service.ts` — `saveProduct`/`deleteProduct` переезжают на `syncEngine.addOperation`, наружу остаются `Promise`-методами.
- `catalogue-entry-edit-form.ts` — только чтение ошибки (`error.body` вместо `HttpErrorResponse.error`), структура метода не меняется.
- Не трогает: сами 12 существующих вызовов `addOperation` (дневник, деньги, настройки) — совместимость по типам, поведение не меняется, кроме мгновенного вместо отложенного отказа на terminal-ошибках (см. пункт 3).

## Затронутые флоу

| Флоу | Сейчас | После |
|---|---|---|
| Сохранить продукт (успех) | Прямой запрос, `await` | Через движок, non-optimistic — тот же момент ответа, та же реакция |
| Сохранить продукт — «уже существует» | Форма показывает текст сразу после ответа | То же самое, тот же текст, тот же момент — источник данных теперь `error.body` вместо `HttpErrorResponse.error` |
| Удалить продукт — «используется в дневнике» / «не найден» | Показывается сразу | Не меняется |
| Сохранить/удалить продукт — сеть недоступна/сервер не отвечает | 1 попытка, ошибка сразу | Теперь до 3 попыток с паузой (~6с) прежде, чем показать ошибку — движок сам восстановит соединение, если оно моргнуло. Небольшое изменение: раньше — мгновенный отказ при любом сбое, теперь — попытка дождаться. Считаем улучшением (соответствует тому, как уже ведёт себя дневник/деньги), но это единственное реальное изменение поведения в этом плане, стоит отметить явно |
| Правка дневника / денег — терминальная (не сетевая) ошибка, например «запись не найдена» | Три бессмысленных повтора (~6с), потом общий текст ошибки | Мгновенный отказ, тот же общий текст — быстрее, поведение по существу то же |
| Правка дневника / денег — сетевая ошибка/таймаут | Три повтора, как сейчас | Не меняется |

## Реализовано (2026-08-02)

- `sync-engine.service.ts` — `SyncOperationError {status, body}`, `normalizeSyncError`/`isRetryable` (retryable: status 0/429/5xx; terminal: прочий 4xx), `runOperation` сдаётся сразу на terminal-ошибке. `rollbackCallback`/`errorCallback` расширены до `(error: SyncOperationError) => void` — ни один из 12 существующих вызовов не тронут, компилируется без правок в них (структурная совместимость по числу параметров).
- `food-catalogue.service.ts` — `saveProduct`/`deleteProduct` теперь строят `new Promise(...)` вокруг `syncEngine.addOperation` (`NonOptimistic`, без `feedback`), наружу остались обычными `Promise`-методами.
- **Найдена и попутно исправлена находка**: сравнение ошибок в `catalogue-entry-edit-form.ts` (`'Product is used in diary entries'`, `'Product not found'` — с большой буквы) никогда не совпадало с реальным телом ответа сервера (`'product is used in diary entries'`, `'product not found'` — с маленькой, см. бэкенд-документ). То есть ветка «используется в дневнике» в форме удаления не срабатывала уже до этой правки — пользователь всегда видел общий текст «Не удалось удалить продукт» вместо конкретного объяснения. Исправлено регистром при переносе на новый источник ошибки (`error.body` вместо `error.error`).
- `catalogue-entry-edit-form.ts` — структура не менялась (осталось `await`/`try/catch`, как и уточнено в «Направление» выше), поменялись только два места чтения тела ошибки.
- `tsc --noEmit` и `ng build --configuration dev` — чисты.
