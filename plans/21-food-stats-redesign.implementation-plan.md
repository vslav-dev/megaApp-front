## Что делаем и зачем

Дневник еды и статистика — один экран, а не два раздела, между которыми переключаются через меню. Дневник (список записей, ввод еды/веса) всегда на месте, статистика подстраивается под то, сколько для неё осталось места:

- **Мало места (телефон)** — статистики "рядом" физически нет, весь экран — один столбец. Под дневником (под кнопкой "Добавить") — ряд кнопок-тумблеров, по одной на каждый блок статистики, плюс кнопка "Развернуть всё/Свернуть всё". Каждый тумблер независимо показывает/прячет свой блок прямо в этом же столбце, ниже кнопок — без перехода на другой экран, без роута, без пункта меню.
- **Больше места** — рядом с дневником появляется отдельный столбец статистики, все блоки в нём открыты всегда, тумблеры пропадают за ненадобностью.
- **Ещё больше места** — этот столбец статистики сам разъезжается на два столбца (те же блоки, просто в 2 колонки вместо одной) — тот же принцип автоподбора числа колонок, что уже есть в `metric-card-grid` (модуль метрик): чем шире контейнер, тем больше колонок влезает.

В статистику встраиваются 5 новых карточек из концепта: лента-30-дней (1B), streak (3), топ-продукты (7), объединённая карточка вех+итогов пути (15+16, по пожеланию пользователя — возможно скрестить). Два существующих графика (вес, ккал/цель) **не переписываются** — весь Chart.js-код остаётся как есть, просто становится ещё одним блоком статистики (самым широким — всегда на всю ширину области статистики, в любом режиме).

Статистика включает сегодняшний день по умолчанию (оба старых графика точно). Для новых карточек (в первую очередь streak) исключение сегодня решается отдельно, не общее правило — см. открытые вопросы.

- `services/food/food-stats.service.ts` — `stats$$` из `GET /api/food/stats` (`Stats = { [dateIso]: DayStats }`, `DayStats = {weight, weightAvg, consumedKcal, targetKcal, isVirtualKcalDay}`, именованный тип по плану `19`), localStorage-кэш, производные `statsChartData$$`/`statsChartDataClipped$$` с клиентской агрегацией по неделям/месяцам при широком диапазоне (`prepareAggregatedData`) — единственный существующий прецедент производных вычислений поверх `stats$$`. Побочное наблюдение: `updateStats`/`updateStatsOptimistically` (`:84,481`) оптимистично обновляют `stats$$` сразу после записи, `buildFallbackDayStats` (`:106`) синтезирует день-заглушку для дня, которого ещё нет в `stats$$` (типично — сегодня, до следующего рефетча) — раз сегодня остаётся частью статистики, этот механизм не трогаем.
- Бэкенд отдаёт всю историю целиком (от первой даты пользователя до сегодня включительно) при каждом вызове `/api/food/stats` — для streak/ленты/вех не нужен новый запрос, все нужные дни уже есть в `stats$$` на клиенте. Ответ меняется с плоской карты дней на объект `{days, topProducts, totalEntries}` (см. парный бэкенд-документ) — та же самая одна загрузка страницы, что и раньше, просто несёт больше.
- `metric-card-grid` (модуль metrics) — авто-fit колонки через `ResizeObserver`: измеряет собственную ширину контейнера, ищет число колонок N, при котором фактическая ширина колонки (доступная ширина минус зазоры, делённая на N) ближе всего к целевой ширине (алгоритм и обоснование гистерезиса — в `plans/14-responsive-metric-card-grid...implementation-plan.md`). Компонент как целое жёстко завязан на `MetricChartCardData` и настройки метрик — не импортируем напрямую, но сам алгоритм подбора N используется и здесь (см. ниже).
- `money-screen.html` — фиксированный 2-колоночный flex без мобильной адаптации; не образец для нужного поведения.
- ui-kit: `v-card` (обёртка), `v-progress` (линейный прогресс-бар, цветовые классы `.v-primary/.v-danger/.v-accent`), `v-button`. Нет готового кольца-прогресса/бейджа — если стрик оформится кольцом (вариант A концепта), кольцо рисуется инлайново (SVG) внутри карточки. `v-expand`/`v-accordion` не используются — тумблеры реализуются набором независимых булевых сигналов (см. ниже), не через готовый accordion-компонент (тот рассчитан на один открытый элемент группы, а тут нужна независимая мультивыборка).
- Темизация: `--v-color-*` custom properties (`--v-color-surface`, `--v-color-success/warning/danger`, `--v-color-text[-muted]`, ...), тёмная тема — класс `.dark` на `<html>`, тема-палитра — атрибут `[v-theme='flat-blue']`. Новые карточки красятся только этими токенами, светлая — дефолт, тёмная проверяется вручную по ходу вёрстки.

## Ключевое архитектурное решение

Мёртвая колонка `catalogue` и весь механизм "мобильный роут-переключатель секций" (`selectedFoodSection`, `food/:section`, отдельный пункт "Статистика" в глобальном меню) — убираются полностью, не адаптируются. Взамен — раскладка, управляемая исключительно шириной доступного пространства, без роутов и без пунктов меню.

Логика графиков и агрегации (`FoodStatsService`, `chart-config.ts`) не переписывается — устойчива, не имеет отношения к раскладке. Существующий `food-stats.ts` (два графика + слайдер) переименовывается в `food-stats-charts` без изменения внутренней логики — просто один из блоков статистики, наравне с новыми карточками, без специального сворачивания/разворачивания на его уровне (тумблер-логика — общая для всех блоков, на уровне контейнера, не внутри самого графика).

Контракт `/api/food/stats` расширяется (см. парный бэкенд-документ): `{days, topProducts, totalEntries}`. `FoodStatsService` разбирает новый конверт, `stats$$` строится из `response.days` (нынешние потребители не меняются), плюс новые сигналы `topProducts$$`/`totalEntries$$`.

Для производных данных новых карточек — отдельный вычислительный сервис `FoodStatsInsightsService` (без своего сетевого запроса) поверх `FoodStatsService.stats$$` + проброс `topProducts$$`/`totalEntries$$`.

## Раскладка — автоподбор режима по ширине

Единственный источник решения — `food-screen.ts`: один `ResizeObserver` на контейнер страницы (та же техника, что в `metric-card-grid`, не булевы брейкпоинты `deviceInfoService` — нужна непрерывная ширина в px). Считается `totalColumnCount$$` — **общее число колонок на экране, включая колонку дневника** (не число колонок одной только статистики):

- **`totalColumnCount$$() === 1`** (влезает только дневник, для статистики рядом места нет) → раскладка одним вертикальным столбцом: `<food-diary/>`, затем `<food-stats-accordion/>` прямо под ним, в том же столбце.
- **`totalColumnCount$$() >= 2`** → раскладка строкой: `<food-diary/>` (фиксированная целевая ширина `~394px`, как у существующих колонок) рядом с `<food-stats-columns [columnCount]="totalColumnCount$$() - 1" />` (оставшееся пространство, без тумблеров — все блоки открыты всегда). При значении 2 — один столбец блоков статистики; при 3 (или больше, если однажды влезет) — те же блоки раскладываются по `grid-template-columns: repeat(N, 1fr)`, где `N = totalColumnCount$$() - 1`, в порядке DOM (без балансировки высот — так же, как сейчас работает `metric-card-grid`).

Дневник считается за первую колонку в этом счёте — если помещается только он, это `totalColumnCount = 1`, а не `0`. Число колонок статистики — всегда `totalColumnCount - 1`, столбец статистики появляется начиная с `totalColumnCount = 2`.

Оба режима показывают одни и те же 5 блоков в одном и том же порядке: лента-30-дней → streak → топ-продукты → вехи+итоги → графики (график — всегда на всю ширину области статистики, `grid-column: 1 / -1`, независимо от числа колонок).

Алгоритм подбора числа колонок — не импортируется из `metric-card-grid` (тот жёстко завязан на `MetricChartCardData`), а переносится/копируется как самостоятельная функция в модуль еды: два места применения — не повод пока заводить общий cross-module utility (если паттерн понадобится в третий раз где-то ещё — тогда стоит вынести в общее место, не сейчас).

## Мобильный режим (`totalColumnCount === 1`) — тумблеры

`food-stats-accordion` — ряд из 5 кнопок-тумблеров (по одной на блок, тот же порядок: лента/streak/топ-продукты/вехи/графики) + отдельная кнопка "Развернуть всё"/"Свернуть всё". Каждая кнопка переключает независимый булев сигнал "открыт ли этот блок" — не эксклюзивный выбор (можно открыть два и больше одновременно). Открытые блоки рендерятся сразу под рядом кнопок, в фиксированном порядке, друг под другом. По умолчанию все блоки закрыты, единообразно, без специального случая для графика.

## Новые карточки (детали по концепту)

- **Лента-30-дней** (`food-stats-heatmap-strip`) — 30 кругляшков, цвет = бэнд дня (недобор/норма/небольшой перебор/сильный перебор) по `ConsumedKcal/TargetKcal` из `stats$$`, чисто клиентский расчёт. Сегодня исключён (см. решённые вопросы) — лента показывает последние 30 завершённых дней.
- **Streak** (`food-stats-streak`) — вариант B (две плашки: "текущая серия" / "рекорд"), из тех же бэндов, что и лента (общий бэнд-хелпер). Успешный день — строго бэнд "норма". Сегодня исключён из подсчёта.
- **Топ-продукты** (`food-stats-top-products`) — топ-5 продуктов по вкладу в ккал за последние 30 завершённых дней (то же окно, что и лента, сегодня не включён). Данные — `topProducts$$` из ответа `/api/food/stats` (абсолютные ккал); процент вклада считается на фронте делением на сумму `consumedKcal` за то же окно из `stats$$`.
- **Вехи + итоги пути** (`food-stats-milestones`) — объединяет 15 и 16: "год назад сегодня" (вес тогда/сейчас + дельта — без "% от нормы": для веса нет отдельной целевой метрики в данных, только для ккал; упрощено до чистого сравнения весов, как в демо-концепте), личные рекорды (мин/макс вес, самый калорийный день, лучшая серия — из `stats$$`), итоги пути (дней ведения, изменение веса с начала — клиентски; точное число записей — `totalEntries$$`). График среднего веса по годам (часть идеи 16 в концепте) не реализован — не было в финальном списке полей карточки, только в раннем концепте.

## Общий бэнд-хелпер

`src/app/shared/food-day-band.ts` — чистая функция/константа бэндов (`as const` объект + производный тип, по конвенции Angular-правил проекта), используется и лентой, и streak-ом. Пороги (строгие, согласовано с пользователем): недобор `<50%`, норма `50–101%`, небольшой перебор `101–125%`, сильный перебор `≥125%` от `targetKcal`.

## Решённые вопросы

- Целевая ширина колонки — `394px`, как у существующих колонок (подтверждено кодом `food-screen.html`, не гипотеза).
- Пороги бэндов дня — строгие (см. выше).
- Успешный бэнд для streak — строго "норма".
- Сегодня исключается из ленты-30-дней и streak (день не завершён); контракт бэкенда приведён в соответствие (см. парный бэкенд-документ — окно `topProducts` тоже не включает сегодня).
- Streak — вариант B (две плашки).
- Набор полей вех+итогов — см. выше.
- Иконки/подписи тумблеров `food-stats-accordion` — текстовые лейблы без иконок (Лента / Серия / Топ продуктов / Вехи / Графики), решено на вёрстке ради простоты.

## Код-ревью — найденные проблемы (после полной реализации)

Ревью всего диапазона фронт+бэк относительно `release`, со сверкой с планом. Ниже — что не так, почему это плохо и как исправить, простым языком.

### 1. ✅ "Год назад" в вехах не работает у части пользователей (баг с датами) — исправлено

**Где:** `src/app/services/food/food-stats-insights.service.ts`, метод `isoMinusYears` (строка ~190).

**Что сейчас происходит:** чтобы посчитать "год назад" для карточки вех, код берёт сегодняшнюю дату-строку (например `"2026-06-17"`), скармливает её в `new Date("2026-06-17")`, отнимает год через `setFullYear`, потом достаёт обратно год/месяц/день через `date.getFullYear()`/`getMonth()`/`getDate()`.

**Почему это плохо:** `new Date("2026-06-17")` (дата без времени) JS всегда парсит как **полночь по UTC**. А `getFullYear()`/`getMonth()`/`getDate()` потом читают эти же данные **в локальном часовом поясе браузера**. Если пользователь сидит в часовом поясе западнее UTC (например, США), то UTC-полночь 17 июня у него на часах — ещё вечер 16 июня. В итоге код вычисляет "год назад от 16 июня", а не от 17-го. Дальше этот неверный день ищется в списке дней пользователя (`allDays.find(...)`) — либо совпадения не находится вообще (тогда карточка "год назад" просто тихо не показывается, без ошибки), либо, что хуже, подставляется вес совсем другого дня.

Рядом же, в `streak.ts` (функция `mondayIndex`), та же самая задача (взять дату-строку и получить день недели) решена правильно — там дата создаётся через `new Date(year, month-1, day)` из уже распарсенных чисел, без прохода через UTC-парсинг строки. То есть в одном файле — правильный паттерн, в соседнем — сломанный.

**Как исправлено:** `isoMinusYears` больше не создаёт `Date` вообще — год вычитается прямо из первых 4 символов строки-даты (`Number(dateIso.slice(0, 4)) - years`), остаток строки (`-MM-DD`) приклеивается обратно как есть. Часовой пояс браузера в этой операции больше не участвует.

### 2. ✅ На очень широких экранах статистика оставляет пустую колонку — принято как есть, won't fix

**Где:** `src/app/components/food/stats/food-stats-block.ts`, функция `getFoodStatsColumns` (строка ~41); алгоритм подбора числа колонок — `src/app/components/food/food-screen.ts`, `totalColumnCount$$`.

**Что сейчас происходит:** раскладка блоков статистики по колонкам захардкожена вручную только для 1, 2 и 3 колонок. Если алгоритм подбора ширины (`food-screen.ts`) решает, что колонок статистики должно быть 4 или больше (это реально на широком мониторе — целевая ширина колонки 400px, значит от ~2000px свободного места алгоритм уже добавит 4-ю колонку), функция берёт готовую раскладку на 3 колонки и просто дописывает к ней пустые массивы `[]` для лишних колонок.

**Почему это плохо:** пустой массив — это пустая колонка в вёрстке. Пользователь на широком мониторе увидит: 4 карточки статистики (Серия/Вехи/Графики/Топ продуктов) втиснуты в первые 3 колонки, а 4-я колонка сетки — просто голая пустота на четверть ширины блока статистики. Место есть, а контент туда не переезжает.

**Первая попытка (откачена пользователем):** ширину колонки жёстко зафиксировали на 400px (`repeat(N, 400px)` вместо `1fr`), число колонок ограничили потолком в 4, лишнее место отдавали под `justify-content: center`. Результат не понравился — пропал прежний плавный ресайз (колонки при сужении/расширении окна плавно меняли ширину, подстраиваясь под доступное место), вместо этого раскладка стала жёстко скакать между фиксированными состояниями. **Полностью откачено** — `food-screen.ts` и `food-stats-block.ts` возвращены к исходному алгоритму (растягивающиеся `minmax(0, 1fr)`-колонки, без верхнего потолка на число колонок, без `justify-content`), проверено `git diff` против коммита до правки — ноль отличий.

**Статус: подтверждено пользователем как won't fix, код не трогаем.** Целевая аудитория этого экрана — сам пользователь на своём мониторе, где раскладка выглядит нормально; сверхширoкие мониторы за пределами этого сценария не в скоупе продукта. Алгоритм подбора ширины (`food-screen.ts`) и раскладка блоков (`getFoodStatsColumns`) остаются как были до этого пункта ревью — исходный плавно-ресайзящийся `minmax(0, 1fr)`-алгоритм без верхнего потолка на число колонок (см. выше, "Первая попытка... откачена").

### 4. ✅ Лишняя обёртка вокруг сигналов без всякого смысла — исправлено

**Где:** `src/app/services/food/food-stats.service.ts`, строки 30–33.

**Что сейчас происходит:**
```
private readonly topProductsSignal$$ = signal([]);
public readonly topProducts$$ = computed(() => this.topProductsSignal$$());
```
То есть публичный сигнал `topProducts$$` — это `computed`, который не делает вообще ничего, кроме как читает и тут же отдаёт значение другого сигнала. То же самое для `totalEntries$$`.

**Почему это плохо:** `computed()` в Angular нужен, когда из одних данных вычисляются другие (как, например, `statsChartData$$` чуть ниже в этом же файле — там реально есть преобразование). Здесь же преобразования нет — это просто лишняя прослойка, которая ничего не добавляет, кроме путаницы: читая код, приходится специально проверять, вдруг внутри `computed` что-то всё же считается, и только тогда понимать, что нет.

**Как исправлено:** `computed(() => this.topProductsSignal$$())` заменён на `this.topProductsSignal$$.asReadonly()` (то же для `totalEntries$$`) — снаружи виден тот же самый read-only сигнал, без промежуточного слоя, который ничего не вычислял.
