# 36. Унификация фронтенд-телеметрии: performance + errors + logs

Парный план: [megaapp-back/plans/36-telemetry-http-ingest.implementation-plan.md](../../megaapp-back/plans/36-telemetry-http-ingest.implementation-plan.md). Главный по объёму — этот (фронт), бэк — второстепенный.

**Дальнейшее развитие:** адрес и форма запроса из этого плана заменяются единым контрактом приёма — [42-ingest-contract-migration](42-ingest-contract-migration.implementation-plan.md) (бэк: [42-extension-log-ingest](../../megaapp-back/plans/42-extension-log-ingest.implementation-plan.md)). Очередь, окно, чанки и автосбор ошибок остаются как здесь описано.

## Цель

Заменить WS-канал `PERFORMANCE_METRICS_BATCH`/`ACK`, заточенный только под perf-замеры, на общий HTTP-канал телеметрии: performance (как сейчас) + error (авто и ручной) + log (зарезервированный примитив) — единым потоком, без деления событий по типу. Ошибки долетают до бэка без правки кода компонентов, привязаны к userId — можно найти ошибки конкретного жалующегося пользователя.

## Текущая реализация

- `PerformanceMetricsService` (root, providedIn root): user-scoped LocalStorage-очередь, лимит 1 MiB, батч максимум 48 KiB/100 событий, доставка через уже открытый WebSocket с ack-подтверждением, интервал между отправками 60s, `PerformanceObserver` (longtask/event timing), таймеры навигации роутера.
- `record()` **дропает** событие, если WS не подключён (`isConnected$$() === false`) — событие не попадает даже в очередь.
- Ack-протокол: `inFlight`/`ackTimeoutId`, ретрай по таймауту без ack, `firstQueuedAtMs`/`isDrainingQueue` для интервала и дренажа очереди.
- Ошибки фронта нигде не перехватываются: в `main.ts` только `handleNavigationError` на ошибки роутинга (console.error + нотификация), никуда не отправляется.
- Сервис используется (`measure`/`measureAsync`/`record`/`recordAfterPaint`) примерно в 27 файлах — компоненты money/food/metrics, sync-engine, photo-capture и др.

## Решение

### Модель события

Единая форма `TelemetryEvent`, **без дискриминирующего поля** — тип события виден по `operation` (namespaced-строка, как уже принято для perf: `app.route_ready`, `money.chart_render` и т.п.):

- `operation` — существующий perf-неймспейс + новые `error.window`, `error.unhandled_rejection`, `error.manual`, `log.<name>`.
- `elapsedMs`/`renderMs`/`outcome`/`attributes` — как сейчас; у `error.*`/`log.*` часть полей может быть пустой.
- `message`/`stack` — новые опциональные поля, заполняются только для `error.*` (и `message` для `log.*`).

Один общий NDJSON-поток на бэке — отдельного поля/маршрутизации по типу не нужно: поиск по namespace `operation` (`grep '"operation":"error\.'`) в едином файле остаётся быстрым и на больших объёмах, разносить по файлам незачем.

### Транспорт: HTTP вместо WebSocket

- Обычный `HttpClient.post('/api/telemetry/events', batch)` — проходит через уже существующий `AuthInterceptor` (auth cookie + `X-Client-ID` заголовок), никакой новой авторизации не нужно.
- Батчинг-окно вместо фиксированного интервала: очередь пуста и пришло событие → отправляем сразу отдельным запросом, открываем окно на 60s; всё, что приходит внутри окна, просто копится в локальной очереди; по истечении окна — один запрос со всем накопленным, окно закрывается до следующего события.
- HTTP-статус ответа — это и есть подтверждение: 200 → чистим отправленное из очереди; ошибка сети/сервера → остаётся в очереди до следующей попытки (открытие нового окна или следующее событие). Отдельный ack-message с перечнем `eventId` больше не нужен.
- Событие больше не зависит от состояния WS — `isConnected$$`/`wsMessages$`/`sendMessage` из `NetworkService` телеметрии не нужны.
- `pagehide`/`visibilitychange` (скрытие вкладки) — `navigator.sendBeacon` вместо WS-flush; это штатный API именно для "отправить перед закрытием страницы".

### Очередь

- User-scoped LocalStorage, новый ключ (старый `performance_metrics_queue` не мигрируется — диагностические данные, потерять несколько последних записей при деплое не критично).
- Лимит объёма как сейчас (1 MiB), удаление самых старых записей при переполнении, счётчик `dropped` уезжает вместе со следующим успешным батчем.

### Автосбор ошибок

- `ErrorHandler` (Angular DI, `providedIn: 'root'`) — ловит большинство runtime-ошибок компонентов/шаблонов/change detection. Событие: `operation: 'error.angular_handler'`.
- `window.addEventListener('unhandledrejection', ...)` — необработанные отклонённые промисы, `ErrorHandler` их не видит. `operation: 'error.unhandled_rejection'`.
- Ручной API `telemetryService.logError(error, context?)` — для мест с уже существующим `try/catch`. `operation: 'error.manual'`.
- Rate-limit по сигнатуре ошибки (`message` + первая строка `stack`): при зацикленной ошибке (например, падающей каждый render/CD-цикл) не шлём тысячи одинаковых записей — не чаще одной в N секунд на сигнатуру, со счётчиком подавленных повторов в атрибутах следующей отправленной.

### Что убирается

- `PERFORMANCE_METRICS_BATCH`/`PERFORMANCE_METRICS_ACK` из `WebSocketMessageType` и связанные интерфейсы в `shared/types.ts`.
- Ack/retry-логика (`inFlight`, `ackTimeoutId`, `handleAck`), зависимость от `networkService.wsMessages$`/`sendMessage`/`isConnected$$`.

### Переименование

- `PerformanceMetricsService` → `TelemetryService`, файл `performance-metrics.service.ts` → `telemetry.service.ts`.
- `PerformanceMetricRecord` → `TelemetryEvent` в `shared/types.ts` (без поля `kind`).
- Публичный API (`measure`, `measureAsync`, `record`, `recordAfterPaint`) сохраняется без изменений сигнатур — миграция вызывающих мест сводится к замене импорта/имени инжектируемого сервиса.

## Находки после ревью (claude-review, 12.09.2026)

1. In-flight батч ссылается на живой массив очереди — события теряются
   - **Важность:** срочно
   - **Как сейчас работает:** когда `trySend()` отправляет батч, он берёт список событий `this.queue.events` не копией, а прямой ссылкой на тот же массив, что продолжает жить в очереди.
   - **Что не так:** пока запрос летит по сети, новые события (`record`, `logError` и т.п.) добавляются в тот же самый массив через `push`. Когда ответ от сервера приходит, код считает "что сейчас лежит в этом массиве" равным "что реально было отправлено" — и удаляет из очереди всё, что там оказалось на тот момент, включая события, добавленные уже после того, как запрос ушёл на сервер. Такие события молча теряются: они не попали в тело запроса, но помечаются как доставленные и стираются из локального хранилища. Это может произойти с любым событием, записанным во время обычного сетевого round-trip — в том числе с самими ошибками, ради надёжной доставки которых всё это и строилось.
   - **Как поправить:** в момент отправки делать неизменяемый снимок (копию) списка событий и счётчика dropped; удалять из очереди по завершении запроса нужно именно те события, что были в снимке, а не что окажется в текущем состоянии очереди на тот момент.
   - **Как будет работать после правки:** из очереди удаляются только реально переданные на сервер события; всё, что записано, пока запрос был в полёте, останется в очереди и уйдёт следующим батчем.

2. Нет паузы между повторными попытками при ошибке сервера — уходит в частый повтор
   - **Важность:** срочно
   - **Как сейчас работает:** окно батчинга должно ограничивать отправку одним запросом в минуту. Но если батч, отправленный именно в момент закрытия окна, получает ошибку сервера (5xx), код видит, что окно уже закрыто, и тут же открывает новое окно с немедленной повторной отправкой — без какой-либо паузы.
   - **Что не так:** при устойчивой ошибке на сервере (например, диск переполнен и запись телеметрии падает) клиент уходит в быстрый цикл повторных попыток без задержки между ними — ровно то, чего batching-окно и создавалось избежать ("не будем сильно бэк заваливать"). Первая неудачная отправка (сразу после первого события) ждёт окно как положено, а вот повтор, случившийся ровно на закрытии окна, — уже нет, и дальше эта гонка повторяется на каждой следующей неудаче.
   - **Как поправить:** не открывать новое окно немедленно после неудачи, если оно закрылось только что по таймеру — ждать полное окно (60s) перед следующей попыткой, как и для первой неудачи.
   - **Как будет работать после правки:** при устойчивой ошибке на бэке повторные попытки идут не чаще одного раза в минуту, независимо от того, на каком этапе окна произошла ошибка.

3. Нет ограничения размера одного запроса — переполненный батч не ретраится, а стирается целиком
   - **Важность:** срочно
   - **Как сейчас работает:** `trySend()` всегда отправляет весь текущий список событий из очереди одним запросом, без ограничения по количеству/объёму (старое ограничение в духе "не больше 100 событий/48 KiB за раз" из WS-версии при переписывании потерялось). Бэкенд (`internal/telemetry/batch.go`) как раз проверяет именно этот лимит — 100 событий, 48 KiB на батч — и отвечает `400`, если он превышен, не записывая ничего. Фронт же трактует любой `4xx`-ответ как "батч плохой, ретраить бессмысленно" и удаляет его из очереди целиком.
   - **Что не так:** если очередь успела разрастись (например, копилась минуту во время сбоя, см. находку 2) настолько, что превысила лимит бэка, весь этот накопленный батч не режется на части и не повторяется — он в один момент необратимо стирается из локальной очереди, потому что код не различает "батч физически некорректен" от "батч просто слишком большой, отправь его частями". Теряется именно тот кусок телеметрии, который отражает сам инцидент — то есть данные, ради которых вся система и строилась.
   - **Как поправить:** вернуть в `trySend()` нарезку очереди на батчи, не превышающие серверный лимит (по числу событий и по байтам), и отправлять/ретраить их по частям, а не всю очередь одним запросом.
   - **Как будет работать после правки:** при любом объёме накопленной очереди на сервер уходят батчи в пределах его лимита; ни один батч не отбрасывается из-за одного только размера.

## Правки после находок (12.09.2026)

Все три находки исправлены одним общим редизайном доставки в `TelemetryService` (заменяет `openWindow`/`trySend`/`onSendSettled` на `maybeStartCycle`/`trySend`/`buildChunk`/`onChunkSettled`):

- Раз в минуту стартует "цикл отправки" (`nextCycleAllowedAt`, не чаще одного раза в `BATCH_WINDOW_MS`) — первое событие в пустую очередь запускает его сразу же, синхронно.
- Внутри цикла очередь режется на чанки (`buildChunk()`) по serverside-лимиту (число событий/байты) — чанк всегда снимок (`slice`-подобный, новый массив), а не ссылка на живой `queue.events`, что и чинит находку 1.
- Успешный чанк удаляется из очереди по своим `eventId`, и если в очереди ещё что-то есть — следующий чанк уходит немедленно, без ожидания окна (быстрый дренаж очереди, как просил пользователь).
- Неудачный чанк (5xx/сеть) останавливает дренаж полностью — следующая попытка только через полный `BATCH_WINDOW_MS` от начала цикла, без немедленного повтора (чинит находку 2).
- Лимит батча поднят с унаследованного от WS-фрейма `48 KiB`/`100` событий до `512 KiB` (половина от `MAX_REQUEST_BODY_BYTES`, с запасом) / `1000` событий — синхронно на фронте (`MAX_CHUNK_BYTES`/`MAX_CHUNK_EVENTS`) и бэке (`maxBatchBytes`/`maxBatchEvents` в `internal/telemetry/batch.go`), закрывает находку 3.
- Добавлены тесты на дренаж по чанкам и на отсутствие немедленного повтора при сбое посреди дренажа (`telemetry.service.spec.ts`).
- Осознанно не стали добавлять отдельный сбор метрик о состоянии самой очереди (размер, разрывы соединения и т.п.) — это уже покрыто существующими `dropped`/`queueDroppedBeforeBatch` и `device.connectionType`/`connectionRtt` в каждом событии; вернуться к этому, если анализ реальных логов покажет, что этого недостаточно.
- `tsc --noEmit`, фронтовые unit-тесты (212/212), `go build`/`go vet`/`go test ./...` — зелено.

## Архитектурный самоаудит (12.09.2026, по правилу "No Lingering Workarounds")

Проверка: не является ли что-то в получившемся коде обходным решением, которое стоило сразу довести до архитектурно верного. Парная находка на бэке (дублирование append+rotate примитива между `internal/telemetry/writer.go` и `internal/metrics/outbox.go`) — в [megaapp-back/plans/36-telemetry-http-ingest.implementation-plan.md](../../megaapp-back/plans/36-telemetry-http-ingest.implementation-plan.md). На фронте:

1. **Рассмотрено и отклонено — очередь `TelemetryService` не объединять с `SyncEngineService`.** Обе очереди похожи снаружи (LocalStorage, ретраи), но решают разные задачи: `SyncEngineService` — надёжная доставка доменных мутаций с идемпотентностью и rollback-колбэками при окончательном отказе; `TelemetryService` — fire-and-forget доставка диагностики без отката и без идемпотентности операций. Общая абстракция была бы либо перегружена чужой семантикой (rollback там, где его никогда не будет), либо потребовала бы урезать `SyncEngineService`. Не объединяю — это не тот случай "разного кода, делающего одно и то же", а разные задачи со случайно похожим внешним видом.
2. **Рассмотрено и отклонено — `operation` как namespaced-строка, а не типизированная константа.** По проектному правилу (`frontend-angular.md`, "Domain Constants over Raw Strings") конечные доменные значения не должны быть россыпью строк. Но это правило — про закрытый набор значений, используемых в сравнениях/логике (роли, статусы), где опечатка молча ломает поведение. `operation` — открытая, постоянно расширяемая система тегирования для аналитики (как в любой обсервабилити-системе — Segment/OpenTelemetry и т.п.), где сама суть в низком трении добавления новой точки инструментирования без правки центрального файла; опечатка здесь не ломает логику, только слегка искажает лейбл в логе. Загонять это в закрытый enum — не архитектурное улучшение, а помеха точечно расширять существующий (уже дособиравший ~40+ значений до этой сессии) паттерн.
3. **Мелкое, не архитектурное:** `suppressedErrorCounts`/`errorSignatureLastSentAt` в `TelemetryService` — карты без верхней границы на время жизни вкладки; при очень большом разнообразии уникальных сигнатур ошибок за сессию могут расти. Для одиночного пользователя в одной вкладке риск низкий, отдельного фикса не заводил — если станет заметно, самое простое: чистить записи старше `ERROR_RATE_LIMIT_WINDOW_MS` при каждой новой ошибке.
