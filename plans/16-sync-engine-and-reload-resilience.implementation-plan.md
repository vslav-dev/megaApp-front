# Единый sync-engine (optimistic/non-optimistic) + устойчивость очереди к перезагрузке

Происхождение: вынесено из `15-sync-architecture-refactor.implementation-plan.md` (два пункта чек-листа, не начатых на момент разделения). Документ самодостаточен — реализовать можно без чтения 15, но одна вещь оттуда — жёсткая предпосылка (см. «Область охвата»).

## Что делаем и зачем

Две связанные, но раздельно ценные фичи фронтенда:

1. **Единый доменно-независимый sync-engine** взамен `SyncQueueService`. Сейчас движок очереди умеет только один режим: применить на экране мгновенно, откатить по ошибке. Любая будущая операция, для которой это не подходит (сначала дождаться ответа сервера, потом показать результат), не может пользоваться очередью — придётся городить путь в обход неё, как уже отчасти сделано для части денежных операций. Цель — один механизм, который параметризуется на уровне отдельной операции: optimistic или non-optimistic, — а не переписанный вручную под каждый новый случай.
2. **Минимальная устойчивость очереди к перезагрузке страницы.** Очередь сейчас живёт только в памяти вкладки. Если операция уже отправлена на сервер, но ответ не пришёл, а пользователь в этот момент перезагрузил страницу — фронт теряет её из виду: сервер мог применить изменение, а клиент об этом никогда не узнает штатным путём. Цель — не потерять именно этот момент, без претензии на полноценную офлайн-очередь.

**Жёсткое ограничение**: видимое поведение для еды и денег не меняется. Обе фичи — под капотом; пользователь не должен заметить разницы, кроме того, что реже возможен неконтролируемый разъезд клиента и сервера.

## Текущая реализация (обзор)

- `SyncQueueService` — общая (для еды и денег) очередь: массив операций в памяти, строго последовательная обработка (одна операция за раз, `isProcessing`-флаг), ретраи с задержкой, уведомление об ошибке/успехе, опциональное «висит» уведомление после задержки.
- Единственный поддерживаемый паттерн — optimistic: вызывающий домен (`FoodDiaryService`, `MoneyService`) сам мгновенно меняет локальное состояние **до** постановки в очередь, передаёт `rollbackCallback` (что откатить при неудаче после исчерпания ретраев) и `successCallback` (что сделать при подтверждении, обычно — сверить локальные данные с ответом сервера).
- На каждую операцию при постановке в очередь генерируется `operationId` (стабильный токен на все ретраи этой операции), передаётся во все три типа запросов (create/update/delete, включая тело DELETE) — сервер по нему отличает повтор от нового запроса и отдаёт закэшированный результат вместо повторного применения (протокольная идемпотентность, уже сделана на бэкенде и фронте, см. `15`). **Это ключевая предпосылка фичи 2** — без неё повторная отправка операции после перезагрузки страницы могла бы задвоить уже применённое на сервере изменение.
- Очередь ничего не сохраняет за пределами памяти вкладки — перезагрузка страницы или закрытие вкладки полностью её обнуляет, независимо от того, была операция уже отправлена или ещё только ждала своей очереди.

## Ключевые архитектурные проблемы

1. Optimistic-поведение зашито в контракт вызова (`addOperation` ожидает, что вызывающий уже поменял состояние) — движок не умеет «применить только после успеха».
2. Жизненный цикл операции (поставить → отправить → подтвердить/откатить) нигде не описан формально — это последовательность разрозненных колбэков, которую каждый домен собирает по своему.
3. Очередь не переживает потерю вкладки — ни для уже отправленной операции, ни (что менее критично, см. «Область охвата») для ещё не отправленной.
4. Каждый новый non-optimistic сценарий сегодня вынужден обходить `SyncQueueService` целиком, теряя заодно ретраи, идемпотентность и уведомления, которые даёт очередь бесплатно.

## Направление рефакторинга (решено, не пересматривать без причины)

- **Очередь остаётся одна, глобальная, строго последовательная.** Идея отдельных очередей-линий по домену (чтобы non-optimistic операция не блокировалась застрявшей чужой optimistic) рассмотрена и отклонена в `15`: ответы бэкенда быстрые (обычно <1с), у одного пользователя нет реального сценария столкнуть операции двух доменов в этом окне — для личного приложения это надуманное усложнение. Повторно поднимать вопрос не нужно.
- **Формальный жизненный цикл операции**, общий для обоих режимов: поставлена в очередь → отправлена → подтверждена (успех) или окончательно не удалась (после исчерпания ретраев). Домены параметризуют его данными (эндпоинт, тело запроса, что откатывать при неудаче), а не пишут его заново.
- **Режим — свойство операции, не домена.** У каждой операции при постановке в очередь явно указывается `optimistic` или `non-optimistic`:
  - *Optimistic* (нынешнее и единственное сегодняшнее поведение, сохраняется как есть): вызывающий код меняет локальное состояние сам до постановки в очередь; движок при окончательной неудаче зовёт откат; при подтверждении — зовёт сверку с ответом сервера.
  - *Non-optimistic* (новая возможность): вызывающий код ничего не меняет заранее; движок зовёт колбэк «применить» только после реального успешного ответа сервера; при неудаче — просто зовёт колбэк ошибки (откатывать нечего, ничего не применялось).
  - Ретраи, бэкофф, `operationId`, отложенное «висит» уведомление, финальные уведомления об успехе/ошибке — общая инфраструктура, одинаковая для обоих режимов.
- **Перевод еды и денег на новый движок — без изменения поведения.** Оба домена сегодня целиком optimistic, поэтому перевод на новый API — чистый рефакторинг вызова (заменить прямой вызов `addOperation` на эквивалентный вызов с явным `optimistic`-режимом), а не смена логики. Ощутимого пользователю эффекта нет — просто движок становится готов принять первую non-optimistic операцию в будущем без обхода очереди.
- **Персистентность — только для уже отправленной, но не подтверждённой операции.** Именно этот момент опасен (сервер мог уже применить изменение, а клиент про это не узнает). Операции, которые ещё только ждут своей очереди и не были отправлены ни разу, персистентностью не покрываются — при перезагрузке они теряются так же, как сегодня (см. «Не входит», это осознанно оставлено за рамками минимума).
- **Почему персистентность безопасна и не требует переигрывания колбэков.** Перезагрузка страницы — это всегда полный рестарт Angular-приложения: `FoodDiaryService`/`MoneyService` в любом случае заново тянут свежий снапшот с сервера при инициализации. Значит на момент восстановления никакого «локального оптимистичного состояния», которое нужно было бы откатывать или сверять, уже не существует — оно и так будет переписано свежими данными с сервера. Отсюда следует упрощение: персистентный слой хранит только то, что достаточно для повторной **отправки** запроса (тип операции, эндпоинт, тело, `operationId`) — без функций-колбэков (они несериализуемы и после перезагрузки всё равно не имеют смысла). При восстановлении операция просто дозаправляется на сервер тем же `operationId`:
  - если сервер её уже применил до перезагрузки — идемпотентность (`15`) вернёт закэшированный результат, повторного применения не будет;
  - если не успел — теперь применит.
  - Итоговое состояние экрана в обоих случаях правильное само по себе, потому что оно и так пришло из свежего снапшота, а не из восстановленного колбэка.
- **Хранилище — `localStorage`, с ключом на пользователя.** Не `sessionStorage`: сценарий-триггер включает и закрытие вкладки, не только `F5`-обновление (`sessionStorage` очищается при закрытии вкладки, `localStorage` — нет). То, что `localStorage` заодно переживёт и перезапуск всего браузера — не проблема, а безопасный избыток: повторная отправка по тому же `operationId` идемпотентна в любом случае, сколько бы времени ни прошло. Запись об операции удаляется из хранилища сразу по её разрешению (успех или окончательная неудача после ретраев) — не копится.

## Область охвата

- Только фронтенд. Бэкенд не меняется — вся необходимая ему инфраструктура (протокольная идемпотентность по `operationId`) уже сделана в `15` и является жёсткой предпосылкой этого плана.
- Домены: еда и деньги — те же два, что перевели на очередь в `15`.
- Естественный порядок реализации внутри плана: сначала переписать движок и перевести на него оба домена (без behavior change), затем добавить персистентность поверх нового движка — это один план, но не обязательно один присест.

## Не входит в этот план

- Полноценная офлайн-очередь, переживающая закрытие браузера как основной сценарий использования (а не безопасный побочный эффект выбора `localStorage`) — избыточно для личного приложения с быстрым бэкендом.
- Расширение персистентности на операции, ещё не отправленные ни разу (сидящие в очереди позади текущей) — технически тем же механизмом, но это сверх зафиксированного минимума; можно сделать отдельным заходом при необходимости.
- Настройки как домен — не переведены на `SyncQueueService` вообще, вне охвата.
- Доменные анти-race механизмы (`pendingDiaryEntryIds`/`mergeServerDiaryResponse` у еды, `pendingTransactionIds`/`mergeSnapshotTransactions` у денег) — закрывают другую гонку (чтение поверх неподтверждённой правки), уже реализованы в `15`, в этот план не входят и не объединяются с sync-engine.
- UX для конфликта версий («протухший ретрай поверх более новой правки») — отдельная тема, отмечена как вне охвата ещё в `15`.

## Чеклист

- ✅ Единый sync-engine (`sync-engine.service.ts`, класс `SyncEngineService`) — взамен `SyncQueueService` (файл удалён). Публичный API — union-тип `SyncOperationInput` (`OptimisticSyncOperation | NonOptimisticSyncOperation`), режим — обязательное поле операции, а не свойство домена. Внутри оба режима нормализуются к общим `onSuccess`/`onFailure` — общая инфраструктура ретраев/бэкоффа/`operationId`/pending-уведомления одна на оба режима, движок не различает их в рантайме, только на границе типов.
- ✅ Еда (6 вызовов), деньги (5 вызовов) и попутно settings (1 вызов, тоже был на очереди) переведены на новый движок с явным `mode: SyncOperationMode.Optimistic` — чистый рефакторинг вызова, поведение не изменилось.
- ✅ Персистентность — перед первой попыткой отправки (не при постановке в очередь) операция пишется в `localStorage` (user-scoped ключ `sync_pending_operation`), без колбэков/feedback. Очищается сразу по разрешению. При старте сессии (`auth.service.ts`: `bootstrap()`-верификация и `login()`) — `restorePendingOperation()` читает запись и отправляет заново тем же `operationId` через тот же движок, тихо (без колбэков — свежий снапшот с сервера и так всё покроет).
- ⭕ Ручная проверка в браузере — не проводилась (правило пользователя: browser-tools не используются для верификации в этой сессии).
- ✅ `tsc --noEmit` чист. Тестов на фронте в проекте нет вообще (0 `*.spec.ts`) — сломать нечего.
