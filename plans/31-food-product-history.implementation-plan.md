# Food Product History — фронтенд (второй план)

## Описание

Новый блок в статистике еды: плюсик открывает поиск продукта (переиспользуя существующий UI поиска), выбранный продукт добавляется в список отслеживаемых (можно несколько одновременно), под списком — обратно-хронологическая таблица всех фактов употребления этих продуктов (дата, граммы, % от нормы, стрелка «перейти на день»), с подгрузкой по скроллу. Каждое изменение состава отслеживаемых продуктов — новый запрос к новому бэкенд-эндпоинту ([31-food-product-history.implementation-plan.md](../../megaapp-back/plans/31-food-product-history.implementation-plan.md)), без кэша и без local-first — обычный HTTP-запрос с честной отменой предыдущего.

Явно отложено пользователем (не в объёме этого плана): график, календарь.

## Текущая архитектура (релевантное)

- Модалка поиска продукта (`FoodSearch`) сейчас на 100% завязана на глобальный `FoodAddModalService` (state machine добавления записи в дневник) и **сама может создавать запись дневника** при выборе продукта с весом в строке поиска — не эмитит событие выбора наружу. Переиспользовать как есть нельзя, требуется разделение.
- Данные поиска приходят по WebSocket (`FoodCatalogueService.searchProducts`), с локальным кэшем каталога — но это именно поиск/подбор продукта, к local-first синхронизации самих записей дневника отношения не имеет. Этот механизм можно и нужно оставить как источник данных для поиска — жёсткое требование «без кэша» пользователь адресовал именно загрузке истории употребления, не автодополнению при поиске.
- Список «Рекорды за всё время» (`Milestones`) — ближайший существующий аналог: ряды выложены `flex` (не grid/`<table>`), из-за чего колонки не выровнены по x — источник жалобы «кривовато». Кнопка «перейти на день» там устроена предельно просто: `foodDiaryService.selectedDayIso$$.set(dateIso)` (+ переключение мобильной вкладки) — никакого роутинга, обычный сигнал. Этот же паттерн — единственно верный способ реализовать «перейти на день» и в новом блоке.
- Блоки статистики — не отдельный роут, а плоский реестр (`FoodStatsBlock` + `getFoodStatsBlockOrder`/`getFoodStatsColumns`), рендерятся то в аккордеоне (мобильный `food-stats-accordion`), то в колонках (`food-stats-columns`). Добавление нового блока — чисто декларативное: новый пункт в реестре, без изменений роутинга.
- В проекте нет прецедента настоящей отмены HTTP-запроса (`switchMap`/`AbortController`) — только guard-флаги и sequence-number-паттерн у WS-поиска. Но `HttpClient` в Angular **отменяет реальный запрос при `unsubscribe()`** — этого достаточно для честной отмены без введения новых зависимостей/паттернов.
- Таблиц (`<table>` или grid-макета) в проекте нет вообще — все списки собраны на flex вручную.
- Оверлея «затемнение поверх существующего контента при фоновой загрузке» в проекте нет — есть только полноэкранный модальный backdrop и спиннеры, которые полностью заменяют контент, а не перекрывают его.

## Архитектурное решение

### Переиспользуемый поиск продукта

Из `FoodSearch` выделяется чисто презентационный компонент — поле ввода + список результатов, без зависимости от `FoodAddModalService`, без побочного создания записей дневника. Наружу — событие выбора продукта. Источник данных внутри — тот же `FoodCatalogueService` (WS-поиск), это не противоречит требованию «без кэша», так как кэшируется только каталог для поиска, а не история употребления.

- `FoodSearch` (флоу добавления в дневник) становится тонкой обёрткой поверх нового компонента: как раньше слушает состояние `FoodAddModalService`, но логику «ввод → результаты → клик» делегирует общему компоненту, оставляя себе только последующую обработку выбора (создание записи с весом и т.д.).
- Новый блок статистики переиспользует ровно ту же модалку, что и «Добавить запись» (`FoodAddModalService` + `<food-search>`), а не заводит собственную: `FoodAddModalService.openForProductSelection(onSelect)` — новый вход в тот же state machine, переводит в состояние `SEARCH` как обычно, но с колбэком выбора продукта, который `FoodSearch` вызывает вместо стандартного перехода в `ADD_DIARY_ENTRY`. Визуально, по анимации, по кнопке закрытия — идентичный опыт с обычным добавлением записи; различается только то, что происходит после выбора продукта.
- Модалка добавления — глобальный `<v-modal>`, управляемый `FoodAddModalService`, ранее жил внутри `FoodDiary` и не рендерился, когда на мобильной раскладке открыта вкладка статистики (а именно там находится новый блок) — поднят на уровень `FoodScreen` (общий родитель `food-diary`/`food-stats-*`), чтобы быть смонтированным независимо от текущей вкладки.

Это осознанный рефакторинг существующего компонента, а не добавление режима/флага поверх старой связанности — жёсткая привязка к global state и скрытое создание записи дневника внутри «поиска» — сама по себе архитектурная проблема, независимо от этой задачи.

### Новый блок статистики

Новый пункт `FoodStatsBlock` (условно `ProductHistory`), свой компонент, регистрируется в порядке блоков и в обеих раскладках (аккордеон/колонки) — без изменений роутинга. Внутреннее состояние компонента (не сервис, не signal-хранилище — сугубо локально, данные не переиспользуются больше нигде):

- список отслеживаемых продуктов (id + имя, имя берётся из результата поиска в момент добавления — бэкенд отдельно за именем не переспрашивается);
- текущая страница рядов истории, курсор следующей страницы, признак «идёт полная перезагрузка» / «идёт подгрузка следующей страницы» (два разных индикатора, не один);
- ссылка на активную HTTP-подписку — на каждое добавление/удаление продукта предыдущая подписка отменяется (`unsubscribe`) до того, как уйдёт новый запрос; это настоящая сетевая отмена, не имитация через флаги.

### Поток данных

Никакого сервиса-обёртки с кэшем — прямой `HttpClient`-вызов к новому бэкенд-эндпоинту из компонента (или тонкого stateless-сервиса без хранения состояния между вызовами, только ради переиспользуемости самого HTTP-вызова).

- Добавление/удаление продукта из списка отслеживаемых → отмена текущего запроса (если есть) → сброс курсора и рядов → новый запрос первой страницы с полным текущим набором id → пока идёт — таблица показывает предыдущие данные, притемнённые оверлеем со спиннером (не проваливается в пустоту и не мигает).
- Пустой список отслеживаемых продуктов → запрос не отправляется, блок показывает пустое состояние («добавьте продукт»).
- Подгрузка следующей страницы (см. ниже) не отменяет и не блокирует полную перезагрузку — это независимый, более лёгкий индикатор снизу таблицы.

### Бесконечный скролл

Sentinel-элемент под последней строкой таблицы + `IntersectionObserver`: при появлении в вьюпорте, если сервер сообщил, что следующая страница есть, и подгрузка ещё не идёт — запрос следующей страницы с тем же набором id и курсором последней полученной строки, результат — добавляется в конец списка (без отмены предыдущих строк).

### Таблица

CSS grid с явным `grid-template-columns` (дата · продукт · граммы · % от нормы · стрелка) — именно то, чего не хватает `Milestones`, чтобы не выглядеть «криво». Колонку продукта имеет смысл скрывать, когда отслеживается ровно один продукт (не обязательный пункт, но дешёвый и полезный штрих). Кнопка «перейти на день» — точная копия паттерна `Milestones.goToDate()` (сигнал `selectedDayIso$$` + переключение мобильной вкладки), никакого нового механизма навигации.

### Оверлей загрузки

Небольшой локальный (не ui-kit, не переиспользуемый компонент — второго потребителя пока нет, выносить в ui-kit преждевременно) абсолютно позиционированный слой поверх таблицы: полупрозрачный `--v-color-surface` (не чёрный `rgba`, чтобы одинаково читался в обеих темах) + существующая разметка спиннера (`animate-spin` + `--v-color-primary`), которая уже используется по всему приложению.

## Упрощение после первой версии: вся история одним ответом (17.10.2026)

Парный блок в бэкендовом плане: [31-food-product-history.implementation-plan.md](../../megaapp-back/plans/31-food-product-history.implementation-plan.md).

Всё выше — первая версия (постраничная подгрузка по скроллу), она реализована, закоммичена и работала. После неё пересмотрено решение; этот блок дополняет план и в части подгрузки заменяет разделы «Бесконечный скролл», двухиндикаторное разделение состояний загрузки и соответствующие пункты «Поток данных».

### Почему отказались от подгрузки

- Объёмы малы (см. бэкендовый блок): тысячи рядов на пользователя, ответ — сотни КБ. Передать всю историю одним ответом не проблема.
- Подгрузка была хрупкой. Во-первых, `loadMore` и полная перезагрузка делили одну подписку: если во время подгрузки сменить набор продуктов, перезагрузка отписывала подгрузку, а флаг «идёт подгрузка» оставался включённым навсегда — дальше подгрузка блокировалась и внизу крутился спиннер. Во-вторых, `IntersectionObserver` срабатывает только при смене пересечения: если после подгрузки sentinel остался на экране, следующая страница не приходила до новой прокрутки.
- Отказ убирает целый класс состояний: курсор, второй индикатор, observer, sentinel.

### Что изменилось

- Один запрос — вся история отслеживаемых продуктов; в запросе только список id. Тип ответа — плоский массив рядов, типы курсора и страницы удалены.
- Состояние загрузки одно (`isLoading$$`, оверлей с притемнением поверх прежних данных). Удалены `loadMore`, курсор, размер страницы, `isLoadingMore$$`, sentinel и `IntersectionObserver` вместе с очисткой в `ngOnDestroy` компонента.
- Таблица рендерит все ряды сразу, без виртуального скролла — для масштаба одного пользователя он избыточен. Разовое построение DOM допустимо, пока скролл после него плавный.
- Решение пользователя: `v-button` в строках пока **не заменять** на нативную кнопку. Сначала проверка на слабом телефоне; если лагает — заменить (риск: в каждой строке два Angular-компонента, `v-button` + `v-icon`, на тысячах строк это тысячи компонентов).
- Лимит продуктов: бэк принимает не более 20 id; фронт зеркалит его константой, кнопка «Добавить» отключается с подсказкой.

## Находки после ревью (v-review:claude, 16.10.2026)

Нумерация общая с планом бэка (находки 4, 6 — там).

1. Фронт не знает про лимит в 20 продуктов
   - **Важность:** стоит поправить
   - **Как сейчас работает:** бэк отвечает 400 на запрос больше чем с 20 id; фронт позволяет добавлять сколько угодно продуктов.
   - **Что не так:** на 21-м продукте вся история пропадает с общей ошибкой «Не удалось загрузить историю продукта», причина непонятна.
   - **Как поправить:** не давать добавить больше 20 (отключить кнопку «Добавить» с подсказкой), лимит держать константой рядом с запросом.
   - **Как будет работать после правки:** 21-й продукт добавить нельзя, ошибки 400 в обычной работе не бывает.

2. Лишняя работа в строке таблицы при каждой проверке изменений
   - **Важность:** стоит поправить
   - **Как сейчас работает:** в каждой строке шаблон заново форматирует дату (создаёт Date), дважды читает сигнал со списком продуктов и ищет имя продукта.
   - **Что не так:** теперь строк тысячи, всё это повторяется для каждой строки при каждом обновлении компонента — на слабом телефоне это лаги.
   - **Как поправить:** один раз посчитать готовые строки (дата, имя) в computed и один флаг «показывать колонку продукта»; шаблон только выводит поля.
   - **Как будет работать после правки:** дата и имя считаются при смене данных, а не при каждой проверке изменений.

3. Нет пустого состояния
   - **Важность:** стоит поправить
   - **Как сейчас работает:** если продукт выбран, но записей нет (или ничего не выбрано), под чипами ничего не показывается.
   - **Что не так:** выглядит как поломка; в чек-листе пустое состояние отмечено сделанным, а в шаблоне его нет.
   - **Как поправить:** добавить короткие тексты: «Выберите продукт» и «Записей не найдено».
   - **Как будет работать после правки:** пользователь видит, почему таблицы нет.

5. Ключ строки в @for всегда сводится к индексу
   - **Важность:** мелочь, но стоит поправить
   - **Как сейчас работает:** ключ собирается из даты, id продукта и индекса.
   - **Что не так:** из-за индекса ключ всегда уникален, то есть это просто «по позиции», а строку для тысяч рядов клеим зря.
   - **Как поправить:** `track $index`.
   - **Как будет работать после правки:** то же поведение, дешевле.

## Выбор продукта для истории находит и архивные (17.10.2026)

Парный блок в плане бэкенда: [31-food-product-history.implementation-plan.md](../../megaapp-back/plans/31-food-product-history.implementation-plan.md). Дополняет план [39](39-food-product-archive.implementation-plan.md) в части режимов поиска.

### Проблема

Пикер истории и добавление еды — один и тот же пикер в одной модалке; история отличалась от дневника только наличием обратного вызова выбора. Поиск не находил архивные продукты, а кнопку «Архив» для режима выбора скрывали (причём «Архив» — режим «только архивные», не «все»).

### Решение

- Режим поиска «архивный / обычный» заменён областью поиска из трёх значений (активные, архивные, все) в сервисе каталога; те же значения идут по WebSocket.
- Область — состояние сеанса модалки, как и раньше режим архива: она не может жить в пикере, потому что пикер пересоздаётся при каждом переходе между шагами модалки (форма добавления, форма продукта и обратно), а область должна пережить эти переходы.
- Кто решает область: сервис модалки при её открытии. Открытие для добавления в дневник — активные, открытие для выбора продукта (история) — все. Прежнее «сбросить режим при закрытии» не нужно: каждое открытие задаёт область заново.
- Пикер больше не получает отдельный флаг «разрешить архивный поиск»: кнопка «Архив» доступна админу, когда область не «все» (во «все» архив уже включён). Состояние одно, второго источника правды нет.
- Старый локальный поиск (по прежним названиям) учитывает ту же область: в истории он тоже находит архивные. Включение старого поиска сбрасывает только архивную область (они по-прежнему взаимоисключающие), «все» не трогает.
- Кэш результатов — только у активной области, как раньше у обычного режима.
- Архивный продукт помечен «архив» в карточке пикера, в чипе отслеживаемого продукта и в колонке «Продукт» таблицы истории: без пометки старый и новый продукт с одинаковым названием не отличить.
- Добавление еды в дневник работает как раньше: область активная, кнопка «Архив» у админа, архивный продукт в дневник не добавляется.

### Чеклист

- ✅ Сервис модалки задаёт область при открытии; убраны сброс при закрытии и флаг «разрешить архивный поиск» у пикера
- ✅ Пометка «архив» в пикере, чипе и таблице истории
- ✅ Спеки: области в сервисе каталога (включая «все», кэш, старый поиск, реалтайм-правки), область по сеансу модалки
- ✅ `tsc`, `ng test`, прод-сборка — зелёно
- ⭕ Вручную: в истории находится архивный продукт и помечен «архив»; в добавлении еды у обычного пользователя архив по-прежнему не находится, у админа работает кнопка «Архив»; светлая и тёмная тема

## Таблица истории: колонка продукта сжимается, заголовок «%» (17.10.2026)

- Колонка даты больше не делит свободное место пополам с продуктом (раньше обе были «1fr»): дата по ширине текста, остальное — продукту.

## Находки после ревью (v-review:claude, 17.10.2026)

Ревью области поиска (области «активные / архивные / все») и правок таблицы истории. Нумерация общая с планом бэкенда (находки 4 и 7 — там).

1. Новый фронт целиком теряет результаты поиска, если бэк старый
   - **Важность:** стоит поправить
   - **Как сейчас работает:** фронт ждёт в ответе поиска обязательное поле «область» и показывает ответ, только если оно равно текущей области на экране.
   - **Что не так:** если фронт окажется выложен раньше бэка (или бэк откатят), ответы придут без этого поля, ни один не совпадёт, и поиск еды перестанет показывать результаты у всех. Обратная сторона: открытая вкладка старого фронта у админа не покажет результаты режима «архив» до обновления страницы.
   - **Как поправить:** кода не менять, соблюдать порядок выкладки (бэк первым, уже записано в плане бэкенда); запасное значение для отсутствующего поля не добавляем, чтобы не плодить заплатки.
   - **Как будет работать после правки:** без изменений в коде; при правильном порядке выкладки окна поломки нет.

2. Пометка «архив» и название в истории берутся из копии продукта на момент выбора
   - **Важность:** стоит поправить
   - **Как сейчас работает:** при добавлении продукта в историю сохраняется его запись из каталога, и чип с названием и колонка «Продукт» читают название и признак архива из этой копии.
   - **Что не так:** если после этого продукт заархивируют, вернут из архива или переименуют (в том числе с другого устройства), каталог обновится, а чип и таблица до перезагрузки страницы покажут старое название и старую пометку.
   - **Как поправить:** хранить в истории только номера продуктов, а название и признак архива брать из живого каталога по номеру (так уже делает топ продуктов).
   - **Как будет работать после правки:** чип и колонка «Продукт» сразу показывают актуальное название и пометку.

3. Область поиска больше не сбрасывается при закрытии модалки
   - **Важность:** мелочь, но стоит поправить
   - **Как сейчас работает:** область задаётся при открытии модалки; при закрытии она остаётся прежней (раньше при закрытии архивный режим выключался).
   - **Что не так:** админ включил «Архив», нашёл продукт, сохранил форму — модалка закрылась без очистки поиска. Область осталась «архивные», последний запрос остался в сервисе, и при переподключении сокета он отправляется заново со старой областью. Результат никто не видит, но это лишний запрос от закрытой модалки.
   - **Как поправить:** вернуть сброс области при закрытии (рядом с очисткой запроса и выбора), а при открытии задавать нужную область.
   - **Как будет работать после правки:** закрытая модалка не держит чужую область, повторных запросов нет.

5. Область поиска меняют три разных владельца
   - **Важность:** мелочь, но стоит поправить
   - **Как сейчас работает:** область лежит в сервисе каталога, при открытии её задаёт сервис модалки, а кнопку «Архив» нажимает пикер через тот же сервис каталога.
   - **Что не так:** чтобы понять, откуда взялось значение, надо читать три файла; новый вызывающий (ещё один выбор продукта) должен знать, что область задаётся через сервис модалки.
   - **Как поправить:** область принадлежит сервису модалки и передаётся в поиск аргументом (циклической зависимости не будет, если каталогу достаточно знать область отправленного запроса). Это не срочно, текущая схема рабочая.
   - **Как будет работать после правки:** одно место, где решается область.

6. Порядок атрибутов в заголовке колонки «%»
   - **Важность:** мелочь, но стоит поправить
   - **Как сейчас работает:** подсказка (title) записана после класса.
   - **Что не так:** по правилам шаблонов статические атрибуты идут перед class и style.
   - **Как поправить:** переставить title перед class.
   - **Как будет работать после правки:** то же поведение, шаблон по правилам.
