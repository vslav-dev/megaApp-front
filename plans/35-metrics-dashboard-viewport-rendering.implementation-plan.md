# 35. Metrics dashboard: viewport-рендер + инкрементальный publish + бинарная персистентность — megaapp-front

Продолжение двух сознательно отложенных пунктов из [front:33](33-metrics-flow-tstorage-migration.implementation-plan.md) (§4): сужение `serviceMetricsData$$` и per-серийная IndexedDB-персистентность. Оба пересмотрены в свете новой идеи — viewport-based рендер, которая делает сужение computed'а снова оправданным (в 33 отклонили, т.к. "открытая панель" дашборда ≈ весь каталог; "видимое во вьюпорте" — уже нет). Плюс одна находка из research-дока [flatline:07](../../flatline/plans/07-metrics-flow-performance.refactoring-research.md) (пункт A5), которая не была реализована ни там, ни в 33.

## 0. Рамки

- **Уже сделано, не в объёме**: подписка per-metric (`MetricsScopeEntry.metricNames`, не service-wildcard) — реализовано в 33, ничего переделывать не нужно. Бинарный wire-формат REST/WS между back/flatline/front — тоже сделан в 33, не трогается.
- **Меняется**: рендер-активация карточек графиков (`metric-chart-card.ts`), сборка `points$$`/публикация из буферов (`metrics.service.ts`), пересчёт карточек дашборда (`metrics-dashboard.ts`), формат IndexedDB-кэша (`metrics.service.ts` + `indexed-db-cache.service.ts`).
- **Не меняется**: `performance-metrics.service.ts`, серверная часть (back/flatline) — весь этот план целиком клиентский рендер/хранение, поверх уже задеплоенного ring buffer из 33.
- **Рассмотрено и отклонено**: web worker под decode/агрегацию точек, OffscreenCanvas для Chart.js. На объёме данных одного пользователя (не сотни параллельных клиентов) это добавляет инфраструктурную сложность без измеримого выигрыша поверх мер ниже — не делаем.

## 1. Текущая реализация (для справки)

- Рендер карточек — без виртуализации по скроллу вообще: `@for (row of dashboardRows$$())` в `metrics-dashboard.html` рендерит все карточки scope одновременно, включая те, что физически ниже видимой области экрана. Каждая — отдельный живой Chart.js-инстанс.
- Данные при этом уже и так текут в буферы независимо от видимости на экране — `MetricsService.buffers` живёт на уровне сервиса (синглтон), не привязан к тому, смонтирован ли конкретный `metric-chart-card`. Это уже соответствует "подписываемся на весь scope, а не только на видимое" — специально переделывать не нужно, только использовать.
- `publishPoints` (`metrics.service.ts:334`) — на каждый merge (REST-ответ или WS-тик) пересобирает плоский `MetricPoint[]` из **всех** буферов по **всем** сериям и пересортировывает его целиком, независимо от того, что реально изменилось за этот тик.
- `serviceMetricsData$$` (`metrics-dashboard.ts:266`) — на каждое изменение `points$$` пересчитывает карточки для всего текущего scope; для дашборда scope ≈ весь каталог dashboard-включённых метрик, независимо от того, сколько из них реально видно на экране в моменте.
- `chart.update('none')` (`metric-chart-card.ts:390`) — анимация на обновлениях уже отключена, резервов на этом уровне больше нет.
- IndexedDB (`metrics.service.ts:416`, `scheduleCacheWrite`) — один `JSON.stringify`-блоб (`STORAGE_KEY = 'metrics_detail'`) на весь набор буферов, debounced 1с; каждая запись сериализует всё целиком, не только изменившееся с прошлой записи.

## 2. Целевая архитектура

### 2.1. Viewport-gated рендер — ядро плана

Каждая смонтированная карточка отслеживает свою видимость через `IntersectionObserver` (не ручной scroll-listener и не проверка на каждое обновление данных — сам observer держит актуальный флаг видимости событийно, дёшево по построению, без polling). `rootMargin` с запасом в обе стороны — активировать чуть раньше входа во вьюпорт, деактивировать чуть позже выхода — чтобы быстрый скролл не дёргал переключение туда-сюда на каждый мелкий сдвиг.

Карточка **не размонтируется** при потере видимости — Chart.js-инстанс и canvas остаются в DOM, просто перестают получать `chart.update()`. Это дешевле честного destroy/recreate (нет повторной инициализации Chart.js/плагинов/цветовой темы на каждый возврат в область видимости) и даёт тот же прирост производительности, что и полное размонтирование — сама отрисовка (пересчёт точек в путь на canvas, layout, перерисовка) и есть дорогая часть, не факт присутствия DOM-узла.

При возврате во вьюпорт — один `update('none')` данными, которые уже накопились в буфере за время невидимости (буфер всё это время наполнялся по WS независимо от видимости карточки — см. §1) — мгновенно, без сетевого ожидания.

### 2.2. `serviceMetricsData$$` — сужение до видимого scope (переоткрытие пункта из 33)

В 33 отклонили сужение до "открытой панели", т.к. для дашборда это давало малый выигрыш (открытая панель дашборда ≈ весь каталог dashboard-выбранных метрик). С viewport-gating появляется по-настоящему узкий критерий — не "что выбрано пользователем", а "что физически видно прямо сейчас (+ rootMargin запас)". Пересчёт серии (не только вызов `chart.update`, но и сама сборка `MetricChartCardSeriesDisplay` — sparse-series, коллапс через `MinuteMetricCollapseCache`) для карточек вне видимой области с запасом пропускается, не только финальная перерисовка.

### 2.3. Инкрементальный `publishPoints` — устранение полного ресорта (находка из research-дока A5, не была реализована)

Сегодня каждый merge пересобирает и сортирует весь накопленный набор точек по всем сериям заново — стоимость растёт с суммарным объёмом буферов (потенциально десятки тысяч точек при широком scope дашборда), а не с тем, что реально пришло за тик (обычно единицы точек по единицам метрик). Поскольку ring buffer уже хранит точки в bucket-адресованных слотах (структурно упорядочены), полная пересортировка на каждый тик избыточна по построению.

Целевая модель — публикация по затронутым сериям, без глобального ресорта всего массива. Это неизбежно требует тронуть внешний контракт `points$$`, который в 33 сознательно оставили плоским ради нулевого риска для потребителей (`metrics-dashboard.ts`/`metric-chart-card.ts`/`metrics-series.ts`). Раз в этом плане `metrics-dashboard.ts`/`metric-chart-card.ts` и так переписываются под viewport-gating (§2.1/§2.2) — контракт меняется одним заходом, а не двумя последовательными переделками потребителей.

### 2.4. Бинарная per-серийная персистентность в IndexedDB (второй отложенный пункт из 33)

Один `JSON.stringify`-блоб (`STORAGE_KEY`) заменяется на per-серийные записи тем же bucket-адресованным форматом, что у живого ring buffer (см. 33 §2.4 — идея не менялась, просто не была реализована). Дополнительно, раз переходим на per-серийное хранение: debounced writer пишет только те серии, что реально изменились за тик, а не весь набор целиком на каждую запись — почти бесплатное дополнение поверх самой миграции формата, но убирает последний источник "сериализуем всё, хотя изменилось немногое" в цепочке.

## 3. Что не меняется — явно

- Подписка per-metric (`MetricsScopeEntry`) — сделана в 33, не трогаем (см. §0).
- Бинарный wire-формат REST/WS back↔front — сделан в 33, не трогаем.
- `chart.update('none')` без анимации — уже так, резервов нет.
- Ring buffer как таковой (`MetricRingBuffer`, ёмкость, bucket-адресация) — не меняется, только то, что вокруг него.
- Различие manual force-refresh / heartbeat, `clearCache()` — не про рендер/публикацию, не меняется.
- `metrics-health.service.ts` (health-dot/summary) — не завязан на `points$$`/буферы, не затрагивается (как и в 33).

## 4. Открытые вопросы для этапа реализации

Оба решены на этапе реализации:

- `rootMargin` — 200px (`VIEWPORT_GATE_ROOT_MARGIN_PX`), константа рядом с остальными magic-number константами `metric-chart-card.ts`.
- Пересчёт для невидимых карточек пропускается полностью, а не частично — `chartUpdateEffect` читает `isVisible$$()` первым и не трогает ни один другой сигнал, пока карточка не видна (см. чеклист §5). Промежуточного "облегчённого" пути не понадобилось: сигналы всегда отдают актуальное значение при первом чтении, так что при возврате во вьюпорт эффект сразу видит свежие данные без отдельного механизма "подхвата" — ни один кадр не показывает пустоту дольше, чем сегодняшний путь монтирования карточки.
