## Цель
- Фронт шлёт телеметрию на единый приём как источник `telemetry`: путь и форма запроса по контракту v1.
- Поведение очереди, батчинга, ретраев, автосбора ошибок — без изменений.

## Текущая реализация
- Сервис телеметрии держит очередь событий (хранится у пользователя в локальном хранилище браузера, лимит 1 МиБ), батчинг-окно 60 с, нарезку по чанкам (до 1000 событий и 512 КиБ), доставку обычным HTTP-запросом плюс `sendBeacon` при закрытии страницы.
- Адрес: `/api/telemetry/events`. Тело: список событий + счётчик потерянных. Ответ: 204; 2xx и 4xx закрывают чанк, сеть и 5xx оставляют в очереди.
- Событие плоское: идентификатор, время (`timestampMs`), сессия, операция, маршрут, исход, поля ошибки, атрибуты, контекст устройства.
- Перехватчик авторизации добавляет `X-Client-ID` ко всем обычным запросам и при ответе 401 сбрасывает сессию. `sendBeacon` заголовков не умеет.

## Решения
- **Адрес:** `/api/ingest/telemetry`. Авторизация единая для всех источников: ключ либо сессия. Фронт ходит по сессии — cookie и проверка same-origin работают как сейчас, пользователь пишется сервером из сессии; ключ фронту не нужен.
- **Очередь и формат события в ней не меняются.** Преобразование «событие → событие контракта» делается в момент сборки запроса, в одном месте. Поэтому переезд не требует миграции локальной очереди: события, накопленные в старой форме, уходят уже новой.
- **Отображение полей:**
  | Контракт | Откуда |
  |---|---|
  | идентификатор | идентификатор события как есть (`<сессия>:<номер>`, уникален) |
  | время | время события |
  | поток | пространство имён операции — часть до первой точки (`app`, `money`, `food`, `metrics`, `error`, `log`); все имена операций уже в формате «пространство.имя» |
  | данные | всё остальное из события без идентификатора и времени |
- Поток по пространству имён сохраняет принцип плана 36 (тип события виден по пространству операции) и даёт серверный фильтр без разбора данных. Операция без точки — целиком как поток; недопустимые символы потока заменяются безопасным значением (поток никогда не должен стать причиной отказа).
- **Размер чанка считается по готовому телу запроса** (с обёрткой), а не по массиву событий: обёртка добавляет примерно 8%, а потолок сервера прежний — 512 КиБ и 1000 событий.
- **Ответ 200 с подсчётом:** для фронта достаточно статуса (2xx — чанк закрыт). Если сервер отверг события (в теле), фронт один раз пишет предупреждение в консоль: это значит, что форма события нарушена, и это баг фронта, а не повод держать событие в очереди (ретрай не поможет).
- **`sendBeacon`:** тот же адрес и та же форма; `X-Client-ID` не отправляется (ограничение API), бэк принимает запрос без него — в записях клиент пустой, а сессия и так внутри самих событий.
- **Прочее поведение без изменений:** 4xx закрывает чанк (в том числе 404, если бэк выключил источник), сеть/5xx оставляют и повторяют не чаще окна; 401 по-прежнему сбрасывает сессию.
- Старый путь на бэке исчезает без алиаса: устаревшие вкладки получают 404 и один раз сбрасывают накопленное.

## Изменения
- Константа адреса приёма.
- Типы: форма запроса и событие контракта; существующий тип события телеметрии не трогается.
- Сборка запроса (одна функция преобразования) используется и обычной отправкой, и `sendBeacon`.
- Подсчёт размера чанка по телу запроса.
- Обработка ответа 200: предупреждение при отвергнутых.
- Тесты сервиса телеметрии: адрес, форма запроса (идентификатор/время/поток/данные), вычисление потока для каждого пространства имён и для операции без точки, размер чанка с обёрткой, предупреждение при отвергнутых, прежнее поведение 4xx/5xx; тестовые ответы 204 заменяются на 200 с подсчётом.
- Проверки: `tsc --noEmit`, unit-тесты фронта.

## Выкат
- Порядок общий с бэком (см. план бэка): env на сервере → бэк → фронт. Между бэком и фронтом старый фронт теряет телеметрию — допустимо.
- После выкатки проверить: файлы телеметрии появляются в каталоге источника на бэке, у записей есть пользователь, поток совпадает с пространством операции.

## Риски
- Формат строк в файлах меняется (вложенные данные вместо плоских полей, поле `user` вместо `userId`, `client` вместо `clientId`): скрипты и фильтры разбора, написанные под старый файл, нужно обновить; старые файлы лежат отдельно.
- `sendBeacon` без `X-Client-ID`: клиент в записях пустой. Идентификатор устройства можно добавить в сам атрибут события позже, если понадобится.
