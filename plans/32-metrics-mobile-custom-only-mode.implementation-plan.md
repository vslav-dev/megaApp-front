# 32. Scope-based `/metrics`: фронтовая часть + мобильный custom-only режим

Продолжение чеклиста [28-frontend-performance.analysis.md](28-frontend-performance.analysis.md) (пункт «спроектировать план рефакторинга — отдельный документ, следующий шаг»). Дополнено свежим разбором одной реальной мобильной сессии (см. §3).

**Три отдельных плана, один рефакторинг.** Изменение затрагивает три репозитория — разнесено по трём документам, каждый описывает только свою часть:
- **Этот документ** — фронт: откуда берётся scope на каждый раздел, замена gap-scan на курсор-на-метрику, мобильный UI-лок.
- [megaapp-back/plans/32-metrics-history-scope-filter.implementation-plan.md](../../megaapp-back/plans/32-metrics-history-scope-filter.implementation-plan.md) — проброс scope через REST/WS, per-client фильтрация рассылки.
- [flatline/plans/06-metrics-history-scope-filter.implementation-plan.md](../../../flatline/plans/06-metrics-history-scope-filter.implementation-plan.md) — фильтр `(service, metricName)` в самом хранилище.

**Статус решения: полный рефакторинг, подтверждён.** `/metrics` перестаёт быть монолитным «качаем всё всегда» — WS-подписка и REST-история становятся scope-based: клиент запрашивает и получает только те метрики, что реально показаны в открытом сейчас разделе страницы. Это касается **всех платформ** (не только мобилки — переключение панелей на десктопе тоже переходит на scoped-запросы, старый «качаем всё» механизм не остаётся жить параллельно). Поверх этого на мобилке — отдельное, независимое ограничение: раздел вообще не даёт переключаться на сервис-панели, жёстко только custom/dashboard.

## 1. Задача

1. **Scope-based данные (все платформы)** — WS-подписка и REST-история ограничены списком `(service, metricName)`, которые реально отображаются в открытом разделе. Переключение раздела = переподписка + докачка только для новых метрик scope.
2. **Мобильный UI-лок** — на мобилке (`DeviceInfoService.isMobileScreen$$`) `/metrics` показывает только дашборд (custom-панель), без переключения на сервис-панели и без возможности их «переставить».

Второе становится дешёвым следствием первого: если раздел на мобилке всегда один (Dashboard, ~5 метрик), scope для него всегда маленький — весь путь данных (WS, REST, IndexedDB, computed) автоматически лёгкий, без отдельной «фильтрации задним числом» на фронте.

## 2. Текущий флоу (весь путь данных)

- **Flatline** (`flatline/internal/metrics/service.go`, `cache.go`) — все точки всех сервисов в RAM-map (`metricCache.series`), без фильтрации по сервису/метрике на любом из своих эндпоинтов (`ListHistory`, `ListSince`).
- **megaapp-back**:
  - `Poller` (`internal/metrics/poller.go`) — фоново, независимо от клиентов, тянет у Flatline ВСЕ сервисы и рассылает всем подписанным клиентам (`BroadcastDetail`).
  - WS `METRICS_SUBSCRIBE` (`internal/metrics/ws_handlers.go`) — без payload, подписка all-or-nothing.
  - REST `/api/metrics/history` (`internal/metrics/http.go:29`) — параметры только `minuteSince/hourSince/daySince`, без списка сервисов/метрик.
- **Фронт** (`services/metrics.service.ts`) — `MetricsService.points$$` копит и кэширует в IndexedDB (`STORAGE_KEY = metrics_detail`) точки всех сервисов на окне `CACHE_WINDOW_SECONDS` (minute 48ч / hour 30д / day 365д), независимо от того, что реально видно на экране.
  - `metrics-dashboard.ts:serviceMetricsData$$` — один общий computed, который на каждое изменение `points$$`/granularity/dashboardSelection строит полные группы+серии для **каждого** сервиса каталога, даже для нераскрытых панелей (DOM их не рендерит — `@if (isServiceExpanded(...))`, но сам computed отрабатывает всё равно).

### Прямой ответ: пойдёт ли SINCE только по 5 графикам?

**Нет.** Ни один слой (WS subscribe, REST history, Flatline API) не умеет ограничивать выдачу списком сервисов/метрик — везде «дай всё с курсора X».

## 4. Итоговая архитектура (решено)

Список `(service, metricName)` — не список сервисов целиком, и **всегда явный, без wildcard** (см. Flatline-план §2.1). Тот раздел, что сейчас открыт на странице, сам формирует этот список перед запросом — вот этот расчёт и есть основная фронтовая работа в этом рефакторинге.

**Важное следствие явного-списка-без-wildcard**: метрика, которую сервер уже шлёт, но которой ещё нет в TS-каталоге (`metrics-catalog.*.ts`), никогда не попадёт ни в один scope и не будет запрошена — «увидеть новую метрику» теперь значит «сначала занести её в каталог фронта», не раньше. Это осознанное решение, принятое ради простоты контракта (см. §4.1 ниже, блок про «Не в каталоге»).

Список прокидывается в WS `METRICS_SUBSCRIBE` payload и в query `/api/metrics/history` (бэковая сторона — [megaapp-back план](../../megaapp-back/plans/32-metrics-history-scope-filter.implementation-plan.md)). Единственный вариант, который реально уменьшает сетевой transfer + JSON.parse, а не только удержание после парсинга — а по цифрам §3 `history_refresh` (17с из ~30с боли) как раз про это.

### 4.1. Откуда берётся scope для каждого раздела

- **Dashboard/custom-панель** — метрики из `dashboardSelection$$`, плюс метрики, на которые ссылаются `compositeDefinitions$$` (каждое определение — это конкретная метрика у serviceA и serviceB; композит сам по себе не отдельная сущность на бэке, это фронтовая арифметика над двумя уже полученными сериями).
- **Панель конкретного сервиса** (десктоп: раскрыл `/spread-capture-bot-v4` и т.п.) — все **занесённые в каталог** метрики этого сервиса (`metricsCatalogKnownNames(service)`), явным списком. Не «всё, что сервис фактически шлёт» — см. следствие ниже.
- **Панель Settings** — не отдельная панель в `expandedPanel$$`, а независимый оверлей-переключатель поверх текущей (`isSettingsPanelExpanded$$`, см. `isServiceExpanded`/`toggleServiceExpanded` в коде) — её открытие/закрытие не меняет scope, им по-прежнему управляет то, что раскрыто в `expandedPanel$$` (Dashboard либо сервис).
- Открыта ровно одна панель за раз (`expandedPanel$$`) — значит в любой момент времени у клиента один активный scope, не объединение нескольких.

**Мёртвый код после этого рефакторинга — удалить, не оставлять**: блок «Не в каталоге» в `serviceMetricsData$$` ([metrics-dashboard.ts:354-368](../src/app/components/metrics/metrics-dashboard/metrics-dashboard.ts:354)) сегодня строит отдельную группу карточек из имён метрик, которые реально пришли в `points$$`, но не описаны в каталоге (`discoveredNames`). Он работает только потому, что сейчас WS/REST unscoped — точка с любым именем может прилететь и попасть в `points$$` даже без записи в каталоге. После перехода на явный scope без wildcard **такая точка никогда не будет запрошена и не прилетит** — `discoveredNames` гарантированно всегда пуст, блок становится недостижимым мёртвым кодом. Удалить вместе с остальными изменениями `serviceMetricsData$$`, не оставлять как «на всякий случай».

### 4.2. Что происходит при переключении раздела

Переключил раздел → посчитали новый список метрик → отправили `METRICS_SUBSCRIBE` с этим списком (сервер **заменяет** прошлый scope этого клиента, не добавляет) → для каждой метрики нового scope посмотрели её персистентный курсор (§4.3): нет курсора — запрос earliest→сейчас, есть курсор — запрос since курсор. Метрики, которые уже были в предыдущем scope и в новом остались, ничего заново не качают — их курсор и так свежий.

### 4.3. Курсор-на-метрику вместо bucket-скана (не патч, а замена механизма)

Подтверждено чтением кода: `firstMissingHistoryBucket` ([metrics-history-range.ts:52](../src/app/shared/metrics-history-range.ts:52)) ищет первый бакет с нулевым счётчиком в **общей** карте `bucketCounts` (`Record<Granularity, Map<bucket, count>>`, [metrics.service.ts:54](../src/app/services/metrics.service.ts:54)) — она не разбита по сервисам/метрикам, инкрементится точкой от любого сервиса. Работает только потому, что REST/WS сейчас всегда отдают всех разом — неважно, чья точка закрыла бакет, дозапрос «since X» всё равно принесёт всех. При скоупинге по списку метрик это ломается: метрика вне подписки может иметь реальную дыру, а общая карта всё равно закрыта чужими точками — скан её не увидит.

**Решение проще патча "сделать per-service"**: заменить bucket-скан на явный курсор **на каждую метрику** (`service+metricName+granularity`), храня его в уже существующем персисте IndexedDB (`MetricsCacheState.historyCheckedThrough`, сейчас одно число на гранулярность → сделать map по метрике). При открытии вида (дашборд/сервис-панель) собираем список нужных метрик → для каждой смотрим её курсор → нет курсора = запрос earliest→сейчас (полный), есть курсор = запрос since курсор. После подтверждённого ответа курсор каждой полученной метрики продвигается до целевого бакета.

Курсор — **на метрику, не на вьюху**: если метрика видна в нескольких местах (дашборд + своя сервис-панель), курсор общий — переключение между ними не дублирует работу.

**Условие безопасности**: курсор двигается вперёд только после подтверждённого REST-ответа, покрывающего диапазон до этой точки — никогда по факту прихода WS-точки в реальном времени (WS может тихо потерять точку без разрыва соединения; если курсор продвинется по случайно долетевшей более новой точке, дыра перед ней останется незамеченной навсегда). При этом условии bucket-скан можно убрать полностью, а не чинить per-service — курсору можно доверять, потому что REST всегда отдаёт полный авторитетный ответ по запрошенному диапазону.

Приём и фильтрация рассылки на сервере (замена scope при повторной подписке, `Realtime.BroadcastDetail`) — бэковая часть, см. [megaapp-back план §3.2-3.3](../../megaapp-back/plans/32-metrics-history-scope-filter.implementation-plan.md).

### 4.5. WS-подписка целиком на реактивный источник правды — все сценарии одним механизмом

Разобрал полный жизненный цикл WS на фронте ([network.service.ts](../src/app/services/network.service.ts)), чтобы убедиться, что ни один сценарий не забыт, а не полагаться на память о том, что вроде бы уже работает.

**Важный факт архитектуры, который меняет дизайн**: WebSocket-соединение — одно на всё приложение, не per-фича. Открывается при логине/восстановлении сессии (`auth.service.ts` → `networkService.connect()`), живёт независимо от того, открыт ли `/metrics` — уход с роута не закрывает сокет, только шлёт `METRICS_UNSUBSCRIBE`. Реконнект (backoff, оффлайн/онлайн, `visibilitychange`) — целиком внутри `NetworkService`, метрики в этом не участвуют, только реагируют на `isConnected$$`.

**Сегодняшний паттерн — три независимых места, откуда может уйти `METRICS_SUBSCRIBE`**: прямой вызов в `subscribe()`, прямой вызов при смене раздела (в новой схеме), и `resubscribeOnReconnectEffect`, реагирующий на `isConnected$$`. Три места, которые обязаны состояние держать в согласии вручную — именно так рождаются «забыли переподписаться в сценарии X».

**Решение — свести к одному реактивному эффекту, не к трём императивным вызовам.** Текущий scope хранится как сигнал (`currentScope$$`, `null` — раздела с графиками не открыто). Один `effect()` читает и `networkService.isConnected$$()`, и `currentScope$$()` — при **любом** изменении любого из двух (подключились / переподключились / сменили раздел) шлёт свежее сообщение: scope не пуст → `METRICS_SUBSCRIBE` с этим scope + since-докачка по курсорам (§4.3); scope пуст → `METRICS_UNSUBSCRIBE`. `setScope(next)` (вызывается и при переключении раздела, и при первом входе на `/metrics`) — это просто `currentScope$$.set(...)`, никакого прямого `sendMessage` рядом. `unsubscribe()` (уход с роута) — тоже просто `currentScope$$.set(null)`: явный `METRICS_UNSUBSCRIBE` для этого случая не нужен отдельной строкой — его посылает тот же эффект, увидев, что scope стал пустым, тем самым действительно остаётся один путь кода на все переходы, а не два.

Так один и тот же путь кода покрывает: первый вход на страницу (scope появился, соединение уже есть), реконнект посреди сессии (соединение появилось, scope уже есть), смену раздела (scope сменился, соединение уже есть) — без трёх мест, которые можно рассинхронизировать по отдельности правкой одного из них.

**Проверенные сценарии — какой из них что покрывает:**

| Сценарий | Что происходит | Чем покрыт |
| --- | --- | --- |
| Первый вход на `/metrics`, сокет уже подключён (обычный случай — сокет живёт с логина) | `setScope` → эффект видит `connected && scope` → шлёт SUBSCRIBE, докачивает по курсорам | эффект §4.5 |
| Вход на `/metrics` в момент, когда сокет ещё не успел подключиться после логина | `setScope` сохраняет scope; когда `isConnected$$` станет true — эффект сам сработает | эффект §4.5 (не нужен отдельный «отложенный» путь) |
| Переключение раздела (Dashboard → сервис-панель), сокет открыт | `setScope` меняет scope → эффект пересылает SUBSCRIBE (сервер заменяет старый scope), докачивает только новое | эффект §4.5 + бэк §3.2 (замена, не объединение) |
| Переключение раздела при разрыве связи (офлайн) | `sendMessage` внутри эффекта тихо не отправится (сокета нет) — не страшно: как только соединение восстановится, эффект перезапустится с уже актуальным (последним выбранным) scope | эффект §4.5, `NetworkService.sendMessage` возвращает `false`, но эффект переспросит сам |
| Обрыв и реконнект посреди сессии (сеть моргнула) | `isConnected$$` false→true → эффект пересылает SUBSCRIBE с тем же scope + форсирует since-докачку по курсорам (не ждёт обычного 250мс-таймера) | эффект §4.5, докачка — §4.3 |
| Телефон свёрнут/заблокирован и возвращён (`visibilitychange`) | `NetworkService` не переподключается, пока скрыто; при возврате видимости — `openIfAllowed()` → `isConnected$$` флип → тот же путь, что обрыв/реконнект | эффект §4.5 — это тот же самый случай «isConnected сменился», отдельно не обрабатывается |
| Несколько вкладок на `/metrics` одновременно | У каждой вкладки свой `clientId` (per-tab `sessionStorage`), свой сокет, свой scope на сервере — не пересекаются | архитектурно уже так, менять нечего |
| Уход с `/metrics` на другой роут | `unsubscribe()`: `currentScope$$.set(null)` + явный `METRICS_UNSUBSCRIBE` | `ngOnDestroy`, без изменений в подходе |
| Обрыв соединения без явного `METRICS_UNSUBSCRIBE` (сеть просто умерла) | На бэке `Hub` уже вызывает `realtime.Unsubscribe(client)` как disconnect-handler ([modules.go:172](../../megaapp-back/internal/httpx/modules.go:172)) — не зависит от того, успел ли клиент явно отписаться | уже работает на бэке, не требует изменений |
| Рестарт/деплой мегабэка | Для клиента неотличимо от обрыва сети — тот же путь реконнекта. Серверное состояние (`Realtime.subscribers`) обнуляется рестартом, но это не проблема: новое соединение — новый `ws.Client`, шлёт свежий SUBSCRIBE сам | эффект §4.5 + курсоры в IndexedDB (клиентские, рестарт бэка их не трогает) — докачается ровно недостающее |

### 4.6. Кэш (IndexedDB) — готов, менять нечего

`IndexedDbCacheService` ([indexed-db-cache.service.ts](../src/app/services/indexed-db-cache.service.ts)) — тонкая обёртка, полностью дженерик по типу значения (`get<T>`/`set<T>`/`remove`, без знания схемы `MetricsCacheState`), поверх сырого `indexedDB`/`createObjectStore` ([idb-cache.ts](../src/app/shared/idb-cache.ts)) — значения кладутся через structured clone, не через ручной `JSON.stringify`, так что вложенный объект (новая форма `historyCheckedThrough` — map по метрике вместо одного числа на гранулярность) сериализуется ровно так же беспроблемно, как текущий. Ни лимитов размера, ни версионирования схемы на этом уровне нет — сужение хранимых данных (меньше сервисов/метрик после scoping) этот слой тем более не заботит, он и с текущим объёмом ничего не знал о его структуре. Менять в `IndexedDbCacheService`/`idb-cache.ts` нечего.

### 4.4. Что осознанно не трогаем на фронте

- **IndexedDB-кэш точек и его pruning** (`prunePoints`, `CACHE_WINDOW_SECONDS`) — логика не меняется, через неё просто в норме будет проходить меньше данных, потому что WS/REST сами начнут присылать меньше.
- **Формат старого `historyCheckedThrough`** (одно число на гранулярность) при деплое просто перестаёт совпадать с новым (map по метрике) — читаем как «курсора нет» и один раз дотягиваем историю заново для всего, что попадёт в scope. Это дисковый кэш, не источник истины — расширять его отдельной миграцией смысла нет.
- **`BroadcastLatest`/health-dot** (`metrics-health.service.ts`, канал `METRICS_LATEST`) — без изменений на фронте, сервер продолжает слать сводку по всем сервисам как раньше (см. бэковый план §3.4).
- Что не трогаем на бэке и во Flatline (труба авторизации, `Poller`, отсутствие версионирования WS-протокола на раскатке) — см. соответствующие планы, здесь не дублируем.

## Находки после ревью (both-review, 08.09.2026)

1. Цепочка автообновления истории может насовсем остановиться
   - **Важность:** срочно
   - **Источник:** Claude + Codex
   - **Как сейчас работает:** `refreshHistory()` в [metrics.service.ts:176-254](../src/app/services/metrics.service.ts:176) сама себя перезапускает: после успешного REST-ответа зовёт `scheduleRefreshCheck()` ([:226](../src/app/services/metrics.service.ts:226)), та ставит таймер на 250мс, он снова дёргает `refreshHistory()`. Отдельного постоянного таймера/поллера нет — это единственный механизм, поддерживающий цикл.
   - **Что не так:** цепочка обрывается в двух местах и не имеет внешнего подстраховщика. (а) В обработчике ошибки ([:237-252](../src/app/services/metrics.service.ts:237)) выставляется только `retryAfterMs = Date.now() + 60000`, но `scheduleRefreshCheck()` не вызывается — таймер, который должен был бы проверить `retryAfterMs` через 60 секунд, никогда не создаётся, и после любого временного сбоя сети/бэкенда докачка истории останавливается навсегда. (б) Даже без ошибки: как только курсоры «догнали» текущий момент, `buildHistoryRequest` возвращает `null` ([:183](../src/app/services/metrics.service.ts:183)), `refreshHistory` выходит раньше `scheduleRefreshCheck()` — а входящие WS-сообщения (`METRICS_UPDATE`/`METRICS_LATEST`, [:117-136](../src/app/services/metrics.service.ts:117)) больше не запускают проверку заново (в отличие от старой bucket-scan версии). Единственное, что реанимирует цикл — смена scope, реконнект или ручной Refresh; новый закрывшийся час/день сам по себе цикл не разбудит.
   - **Как поправить:** в обработчике ошибки тоже вызывать `scheduleRefreshCheck()` (симметрично успеху) — это закрывает срочный, реально частый случай. Дополнительно стоит решить, нужен ли независимый периодический триггер (не только «пока есть невыполненная работа»), чтобы будущие закрытия hour/day-бакетов сами инициировали проверку, а не полагались только на смену scope/реконнект.
   - **Как будет работать после правки:** временный сбой запроса истории приводит к автоматическому повтору через 60 секунд, а не к зависанию страницы до ручного вмешательства или смены раздела; докачка истории продолжает идти в фоне без скрытых мёртвых точек.

2. Скрытые сервисы дашборда всё равно остаются в scope
   - **Важность:** стоит поправить
   - **Источник:** Codex
   - **Как сейчас работает:** видимость сервиса на дашборде — отдельный флаг `dashboardServiceSelection$$` (переключается `toggleDashboardService`, [metrics-dashboard.ts:817-826](../src/app/components/metrics/metrics-dashboard/metrics-dashboard.ts:817)), выбор конкретных метрик внутри сервиса — отдельная карта `dashboardSelection$$`. `dashboardScopeEntries()` ([:958-973](../src/app/components/metrics/metrics-dashboard/metrics-dashboard.ts:958)), которая строит scope для REST/WS, читает только `dashboardSelection$$` и не смотрит на `dashboardServiceSelection$$`.
   - **Что не так:** выключение «Show in dashboard» (`toggleDashboardService(service, false)`) удаляет сервис только из `dashboardServiceSelection$$`, но не трогает `dashboardSelection$$` — ранее выбранные метрики скрытого сервиса продолжают попадать в scope, продолжают запрашиваться по REST и приходить по WS, хотя на экране их карточек уже нет. Это впустую расходует бюджет scope (см. находку 3).
   - **Как поправить:** в `dashboardScopeEntries()` пропускать сервисы, для которых `isDashboardServiceEnabled(service)` (`dashboardServiceSelection$$`) сейчас `false`.

3. Лимит scope (200 пар) не согласован с тем, что реально можно набрать на дашборде
   - **Важность:** стоит поправить
   - **Источник:** Codex
   - **Как сейчас работает:** `megaapp-back/internal/metrics/scope.go` (`maxScopeMetrics = 200`) и `flatline/internal/metrics/service.go` (`maxHistoryScopeMetrics = 200`) независимо отклоняют scope длиннее 200 пар «сервис+метрика». ## Рефакторинг после ревью — анализ и архитектурное решение (08.09.2026)

Сквозной разбор находок 1-5 по всему флоу (Flatline → megaapp-back → фронт), с целью не патчить симптом, а поправить причину там, где она архитектурная. Ниже — рассмотренные варианты и почему выбран именно этот.

### Находка 1 (главная) — цикл автообновления истории

Корень проблемы шире, чем «забыли одну строчку». `scheduleRefreshCheck()`/`refreshCheckTimeoutId` — самоперезапускающийся `setTimeout`, который одновременно отвечает за три разные вещи: (а) быстрый докат сразу после смены scope, (б) ретрай после ошибки, (в) постоянный «пульс», ловящий будущие закрытия hour/day-бакетов. Это три обязанности в одном хрупком механизме, который останавливается насовсем, если очередной тик не нашёл работы (`buildHistoryRequest` → `null`) или упал с ошибкой — реанимировать его после этого может только внешнее событие (смена scope, реконнект, ручной Refresh).

Рассмотренные варианты:
- **Точечно добавить недостающий `scheduleRefreshCheck()` в error-хендлере.** Закрывает только 1(б), не решает 1(в) (застревание в steady-state после успешного доката) — оставляет тот же хрупкий паттерн для следующего похожего бага. Отклонено — это ровно то «костыльное решение», от которого просили уйти.
- **Вернуть перезапуск проверки по каждому входящему WS-сообщению** (как было до этого рефакторинга). Привязывает частоту REST-докачки к частоте прилёта WS-сообщений — косвенно, непредсказуемо, и не сработает вовсе, если WS временно тихий, а scope активен. Отклонено.
- **Выбрано.** Заменить самоперезапускающийся `setTimeout` на обычный `setInterval` — постоянный, предсказуемый «пульс», которым управляет тот же `subscriptionEffect`, что уже владеет жизненным циклом WS-подписки (`isConnected$$ && currentScope$$`): активен → пульс идёт, неактивен → остановлен. Один источник правды для обоих механизмов (WS-подписка и REST-докачка), а не два независимых. Немедленный первый тик при старте пульса (не ждать интервал) сохраняет быстрый докат сразу после смены раздела — даже быстрее, чем было. Проверку бэкоффа (`retryAfterMs`) переносим из отдельного планировщика прямо в начало `refreshHistory()` — пульс тикает всегда по расписанию, а «не рано ли» решает сама функция. Один REST-запрос уже возвращает данные за весь запрошенный диапазон (не постранично), поэтому многошаговая цепочка объективно не нужна была даже до бага — один тик и так закрывает весь докат целиком.

### Находка 3 — лимит scope в 200 пар (пересмотрено 08.09.2026)

Изначально рассматривался как «лимит слишком легко превысить незаметно для пользователя». При повторном разборе с владельцем продукта пришли к более фундаментальному выводу: лимит вообще защищает не от реального сценария.

Проверено по коду: единственные места, что строят scope — `dashboardScopeEntries()` (только вручную включённые карточки, `dashboardSelection$$`), `compositeScopeEntries()` (объединение composite-определений) и ветка одного сервиса (`metricsCatalogKnownNames(panel)` для одного конкретного `panel`). Ни один путь не способен физически собрать «весь каталог целиком сразу» — такого кода просто нет. Число метрик в scope растёт только вручную, по одной карточке за раз, а UI-графики на дашборде и так становятся неюзабельными на глаз задолго до сотни карточек — то есть сама природа UI уже ограничивает scope сильнее, чем любое серверное число.

Рассмотренные варианты:
- **Поднять лимит выше 200.** Не решает вопрос принципиально — просто новое произвольное число вместо старого.
- **Оставить 200, но сделать отказ видимым (первоначальный план).** Лечит симптом (молчание), но сам лимит остаётся артефактом без реальной защитной роли в этой кодовой базе — сервер, требующий scope, никогда не получает вызов, способный собрать «всё».
- **Выбрано: убрать числовой потолок (`maxHistoryScopeMetrics` в Flatline, `maxScopeMetrics` в megaapp-back) полностью.** Раз ни один существующий вызывающий код не может технически превратить scope в «дай всё», отдельный числовой лимит — это защита от сценария, которого сейчас не существует (см. [[feedback_avoid_overengineering_for_scale]]). Если в будущем реально появится код, собирающий unbounded scope (например: новая фича «выбрать все хосты одной кнопкой»), тогда и понадобится новый, осознанно спроектированный предел под тот конкретный сценарий — вводить его сейчас впрок нет смысла.
- **Важно: НЕ убираем остальную валидацию scope** — scope как был обязан быть непустым списком, каждый элемент обязан иметь непустой `service` и непустой `metricNames` — это защищает от другой, реальной регрессии: случайно пустой/nil scope, который бы тихо означал «дай всё» (то самое поведение, от которого весь этот рефакторинг и уходил). Убираем только числовую верхнюю границу, не смысловую проверку формы.
- Уведомление при 4xx-ошибке автообновления (пункт 3 чек-листа ниже) остаётся отдельной, самостоятельно ценной правкой — общая гигиена обработки ошибок (не ретраить молча то, что не транзиентно), не привязанная больше к вопросу лимита.

### Находка 2 — скрытые сервисы дашборда в scope

Не архитектурная проблема, а точечное расхождение: `dashboardScopeEntries()` не применяет ту же проверку видимости сервиса (`isDashboardServiceEnabled()`), которую уже корректно использует `dashboardRows$$` для списка карточек на экране — сейчас существуют де-факто два независимых определения «что показано на дашборде», и они разошлись. Альтернатив не рассматривалось: единственно верный фикс — использовать тот же существующий метод в обеих функциях, чтобы этот класс расхождений не мог повториться в третий раз.

### Находка 4 — коллизия ключа курсора

Выбрано: `JSON.stringify([service, name])` вместо конкатенации через пробел — стандартный однозначный способ собрать составной ключ в TS, ничего изобретать не нужно. Альтернатива с ручным экранированием разделителя отклонена как избыточное усложнение при наличии готового однозначного варианта из коробки.

## Баг, найденный при ручной проверке после рефакторинга (08.09.2026)

Пользователь заметил вживую: при переключении между сервисами на дашборде графики подтягиваются не сразу, а с задержкой (до 60 секунд — период пульса из пункта 1 выше).

**Причина.** В `syncHistoryHeartbeat()` две разные вещи были завязаны на один и тот же флаг «пульс уже запущен» (`historyHeartbeatIntervalId !== null`): (а) не создавать второй параллельный `setInterval` — это правильно, обязано быть идемпотентным; (б) не делать немедленную проверку при активации — а это было ошибкой, немедленная проверка обязана срабатывать при КАЖДОМ переключении на активное состояние (первый заход, реконнект, смена сервиса), а не только при самом первом. Раз пульс почти всегда уже тикает в фоне на странице метрик, переключение сервиса просто ждало следующего тика.

**Фикс.** Разделены два независимых правила: `refreshHistory()` теперь вызывается при каждом переходе в активное состояние безусловно, а `setInterval` создаётся только один раз (проверка идемпотентности осталась только на создании интервала, не на самой проверке).

**Дополнительно найдено при глубоком разборе (не баг из жалобы, а соседний краевой случай той же природы).** Если пользователь переключает сервисы очень быстро — второй раз до того, как первый REST-запрос успел вернуться — `refreshHistory()` тогда молча выходит (защита от параллельных запросов) и теряет запрос под самый последний scope: пользователь снова ждал бы до 60 секунд. Добавлена «отложенная перепроверка»: если проверка пришла, пока предыдущий запрос ещё летит, это запоминается одним флагом (`hasPendingHistoryRefresh`) и как только тот запрос завершается (успешно или с ошибкой) — тут же делается ещё одна проверка, уже под актуальный на тот момент scope. Без отдельного таймера, без отмены запросов «в полёте» — их данные не пропадают, а безопасно вмерживаются как обычно.

**Защита от лишних повторных запросов.** Отдельного ограничения «не чаще раза в N секунд» нет и не понадобилось — `refreshHistory()` и так не уходит в сеть, если для текущего scope уже всё подгружено (сравнение по курсорам). Быстрое переключение туда-обратно между уже просмотренными сервисами лишних запросов не создаёт бесплатно, без дополнительного кода.
