# 22. Дневник еды — переход на снапшоты + сегменты в памяти + IndexedDB

Парный документ: `megaapp-back/plans/22-food-diary-rewrite.implementation-plan.md` — серверная часть (по факту изменений не требует).

Статус: архитектура утверждена (research ниже), это — план реализации. Полный рефакторинг, не патч. Баг с цепочкой запросов при прыжке на далёкую дату чинится как побочный эффект новой архитектуры, сам по себе целью не является.

Правка (2026-08-05, первая): версионирование по дню выкинуто целиком — избыточная сложность ради экономии, которая на текущем масштабе не окупается.

Правка (2026-08-05, вторая): модель "подтверждение по одному дню с debounce" заменена на модель батчей-сегментов (см. ниже) — предыдущая версия на деле была хуже старого поведения (запрос почти на каждую смену дня вместо батчей). Плюс: хранение переезжает с `localStorage` на IndexedDB — снимает вопрос вытеснения полностью, не только упрощает его.

## Что делаем и зачем

Текущая система загрузки/кэша дневника — непрерывный растущий диапазон дат, шаг подгрузки фиксированной константой, один общий блоб `localStorage` на весь когда-либо загруженный кэш, инвалидация только жёстко зашитым окном "сегодня±7" — переписывается полностью. Причина: многолетние костыли поверх костылей, баг с цепочкой запросов — лишь один из симптомов.

Цель: локально-первое приложение — открывается мгновенно с уже готовыми данными, тихо сверяется с сервером в фоне и точечно обновляет то, что устарело. Оптимистичные правки с автосохранением и откатом продолжают работать как сейчас.

## Область охвата

Дневник еды: записи, суммы за день, вес тела, undo удалённого дня — хранение, загрузка, кэш, инвалидация, навигация по датам.

Не входит: справочник продуктов, персональные ккал, статистика (`food-stats.service.ts`) — отдельные подсистемы, к этой архитектуре и к багу отношения не имеют, продолжают работать как есть.

## Research — согласованная архитектура (обоснование)

### Два независимых слоя — не путать друг с другом

Разбор предыдущих версий этого документа свёлся к тому, что путались два разных вопроса, у каждого — своё простое решение:

1. **Что физически лежит на диске между запусками приложения** — решается хранилищем (IndexedDB).
2. **Что мы считаем подтверждённым сервером прямо сейчас, в рамках текущей открытой вкладки** — решается сегментами в памяти (ниже). Сбрасывается при каждой перезагрузке страницы, к диску отношения не имеет.

### Хранилище — IndexedDB вместо `localStorage`-блоба

Сегодня весь дневник — один JSON-блоб в одном ключе `localStorage`, целиком пересериализуется на любую мелкую правку, растёт без ограничений по мере того, как пользователь листает историю.

Оценка объёма: несколько записей в день, по паре сотен байт в JSON, плюс вес тела — за 5 лет набегает от силы низкие единицы мегабайт. При таком объёме:

- IndexedDB — key-value хранилище с O(1) доступом по ключу (дата) и точечной записью одной записи, без пересериализации всего накопленного. Ровно то, что нужно, без обходных путей с ключом-на-день внутри `localStorage`.
- Ничего не вытесняем и никогда не удаляем — на объёме "единицы мегабайт за годы" вопрос вытеснения просто не встаёт, ни на диске, ни в памяти вкладки в рамках одной долгой сессии. Реестра резидентных дней/LRU не заводим.
- Единственная плата — асинхронность: чтение при старте — не синхронное, как из `localStorage`, а через `await`. На объёме "неделя дневника" это единицы миллисекунд, первую отрисовку не задерживает заметно.
- Старый единый ключ `localStorage` (`food_diary`) просто перестаёт использоваться — существующий механизм очистки устаревших версий кэша (`CACHE_SCHEMA_VERSION`, `purgeStaleCacheVersions()`) вычистит его сам, ручная миграция данных не нужна — IndexedDB стартует пустым, первый батч (см. ниже) его наполнит.
- Переключение пользователя/логаут — существующий механизм очистки пользовательских кэшей при смене пользователя расширяется на очистку IndexedDB-хранилища дневника (той же командой, что сегодня чистит `localStorage`).
- Undo-снапшот удалённого дня (`DeletedDiaryDaySnapshot`) — остаётся в `localStorage` как есть: маленький, не растёт со временем, к этой проблеме отношения не имеет.

### Сегменты — в памяти, живут одну сессию

Кэш (IndexedDB) сам по себе не считается ни "свежим", ни "устаревшим" — это только материал для мгновенной первой отрисовки. Правда — всегда то, что приходит с сервера, без предварительной сверки версий: если что-то изменилось, ответ это перезапишет; если нет — перезапись выйдет холостой, и это дешевле, чем сперва спрашивать "изменилось ли".

Чтобы не заваливать сервер запросом на каждый клик влево/вправо, но и не тащить всю историю разом (старый баг), заводится **список подтверждённых в эту сессию диапазонов дат** ("сегментов") — чисто в памяти, не персистится никуда. При перезагрузке страницы список стартует пустым заново — даже если данные по этим дням физически уже лежат в IndexedDB с прошлой сессии, они считаются неподтверждёнными, пока не будут заново получены с сервера.

**Зачем это, а не версия:** сегмент решает ровно ту задачу, которую раньше пытались решить версией — отличить "день внутри загруженного диапазона, но пустой, потому что пользователь ничего не ел" от "день, который мы вообще не спрашивали у сервера". Первый — внутри сегмента, второй — снаружи. Никакого номера версии для этого не нужно, только факт "этот диапазон дат целиком запрошен и получен".

**Правило размера батча:** первый сегмент, запрошенный в рамках сессии (при старте, вокруг сегодня), — маленький, ±7 дней. Абсолютно любой следующий сегмент (продолжение при подходе к краю или прыжок в календарь) — сразу большой, ±30 дней. Не завязано на то, далеко ли дата от сегодня — только на то, первый это сегмент за сессию или нет.

**Правило триггера нового сегмента — одно и то же для всех случаев:** если целевая дата (текущая выбранная, либо та, к которой подходим за 2-3 дня до края существующего сегмента) не покрыта ни одним известным сегментом — запрашивается новый сегмент нужного размера (по правилу выше) вокруг этой даты.

- Пролистывание к краю уже загруженного сегмента — это частный случай того же правила: "первая непокрытая дата впереди" становится центром нового (уже большого, ±30) сегмента, запрашиваем заранее, за 2-3 дня, чтобы пользователь не упёрся в ожидание.
- Прыжок в календарь на любую дату, сколь угодно далёкую, — тоже тот же случай: целевая дата не покрыта ничем → один запрос вокруг неё. Расстояние ни на что не влияет, поэтому цепочка запросов в принципе невозможна — не потому, что где-то стоит проверка, а потому что самого понятия "тянуться от старого диапазона к новому" в системе не существует.
- Если новый/расширенный сегмент соприкоснулся или пересёкся с другим уже существующим — сливаются в один.

Отдельный дебаунс/отмена запросов не нужны: сегменты крупные и запрашиваются редко (раз на ~7 или ~30 переключений дня), скопления параллельных запросов физически не возникает — достаточно не запускать второй запрос за диапазон, который уже в процессе получения.

**Реконнект WebSocket — сознательно не обрабатываем.** Пока вкладка открыта и WS живой, любые правки долетают точечными realtime-патчами (см. ниже) — это отдельный, не связанный с сегментами механизм, работает всегда. Если WS ненадолго отвалился и переподключился без полной перезагрузки страницы — теоретически можно пропустить правку, случившуюся на другом устройстве именно в это окно. Решение: сознательно игнорируем этот риск — покрывает 99% случаев, а при малейшем подозрении на нестыковку пользователь и так перезагружает страницу, что полностью пересобирает сегменты с нуля.

**Несколько устройств открыты одновременно** — не касается сегментов вообще, закрыто существующими realtime WS-патчами, которые работают независимо и не меняются.

### Оптимистичные правки — сохраняются, ложатся на IndexedDB так же просто

Создание, правка, удаление записи, выставление веса — как сейчас: правка применяется оптимистично к данным дня в памяти, сразу пишется в IndexedDB (одна запись на день, без сериализации всего остального), ставится в очередь существующего механизма фоновой синхронизации без изменений в нём самом, при ошибке — откат к снятому перед правкой снапшоту этого же одного дня.

Незакоммиченные правки (в очереди синхронизации, ещё не подтверждённые сервером) защищены так же, как сейчас: ответ на фоновый запрос сегмента не имеет права перетереть день, у которого есть неподтверждённая операция в очереди — для такого дня входящий снапшот игнорируется до разрешения очереди (аналог сегодняшнего `pendingDiaryEntryIds`).

### Realtime-обновления — без изменений в подходе

Точечные патчи по отдельным событиям (запись создана/изменена/удалена, вес обновлён) применяются к дню, если он есть в памяти, — как сейчас. Событие на день, которого нет в памяти, просто игнорируется.

### Undo удалённого дня

Не меняется — отдельный ключ в `localStorage`, к сегментам и к IndexedDB-хранилищу дневника отношения не имеет.

### Серверные изменения — фактически отсутствуют

Сегменты всегда симметричны (центр ± офсет — ±7 для первого сегмента, ±30 для всех остальных) — это ровно та форма запроса, которую уже принимает существующий эндпоинт (`дата + offset`). Менять на бэке нечего, подробности и обоснование — в парном документе.

## План реализации

Порядок — снизу вверх по зависимостям: сначала хранилище, потом сегменты и триггер запроса поверх него, потом переключение мутаций и realtime, в конце — снос старого.

### 1. IndexedDB-обёртка

Небольшой сервис без сторонних библиотек: открытие БД, один object store с ключом `dateISO`, методы "получить день", "получить диапазон дат" (через `IDBKeyRange.bound` — строковые ISO-даты сортируются лексикографически корректно), "записать день", "удалить всё" (для логаута/смены пользователя).

### 2. Типы

- Тип данных дня — без изменений по сути (записи, суммы нутриентов, вес).
- Тип сегмента: `{ start: string; end: string }` — простой список в памяти, без персистентности.
- Тип запроса к серверу — без изменений (дата + offset).

### 3. `FoodDiaryService` — слой хранения

- Заменить `loadDiaryFromLocalStorage()`/`saveToLocalStorage()` (единый блоб) на вызовы IndexedDB-обёртки (шаг 1).
- Все точки, которые сегодня вызывают `saveToLocalStorage(this.diaryRaw$$())` целиком (create/edit/delete записи, delete/restore дня, realtime-хендлеры — их около десятка по файлу), переводятся на запись только затронутого дня (или нескольких дней при restore) через IndexedDB-обёртку.
- Логаут/смена пользователя — добавить очистку IndexedDB-хранилища дневника туда же, где сегодня чистятся пользовательские ключи `localStorage`.

### 4. Сегменты и триггер батча

- Список сегментов в памяти (`WritableSignal<{start: string; end: string}[]>` или обычное поле сервиса) — стартует пустым при каждом создании сервиса (то есть при каждой загрузке страницы).
- Функция "покрыта ли дата X существующим сегментом" + функция "ближайшая непокрытая дата в направлении" — на них строится и обнаружение приближения к краю, и обнаружение прыжка (см. research).
- Размер нового сегмента — ±7, если список сегментов пуст (это первый сегмент сессии), иначе ±30.
- При получении ответа сервера — добавить/расширить сегмент, слить с соприкасающимися существующими.
- Не запускать второй запрос за диапазон, который уже в процессе получения (простой флаг "сегмент такого-то диапазона уже запрашивается").

### 5. Старт приложения и `SYNC_STATUS`

- Конструктор сервиса: асинхронно поднять из IndexedDB то, что физически есть для текущего выбранного дня (по умолчанию сегодня) — использовать для первой отрисовки, не дожидаясь сети.
- Сразу следом, не блокируя рендер, — запустить триггер батча (шаг 4) для текущего выбранного дня, как и для любой обычной смены дня. Раз список сегментов только что стартовал пустым, это гарантированно даёт первый (маленький, ±7) сегмент.
- `SYNC_STATUS` — согласно принятому решению (research), не обрабатывается отдельно; WS-патчи закрывают live-случай, реконнект-разрыв — принятый риск.

### 6. Навигация — снос старой модели диапазона

Убрать: `loadedRange$$`, `FETCH_THRESHOLD`, `FETCH_OFFSET`, `shouldLoadMore()`, `loadMoreData()`, `updateLoadedRange()`, `loadMoreDiaryEffect$$`, `fetchMoreDiaryTrigger$` — заменяются механизмом сегментов (шаг 4). `getFoodDiaryFullUpdateRange(dateIso, offset)` остаётся почти как есть (форма запроса не меняется), вызывается из триггера батча вместо сегодняшнего эффекта.

`mergeServerDiaryResponse` — **не** сносится: это и есть защита незакоммиченных дней от перезаписи ответом сегмент-запроса (см. "Оптимистичные мутации" в research) — та же роль, что и раньше, продолжает использоваться внутри `getFoodDiaryFullUpdateRange`.

### 7. Оптимистичные мутации

`createDiaryEntry`/`editDiaryEntry`/`deleteDiaryEntry`/`deleteSelectedDayEntries`/`restoreSelectedDayEntries`/`setUserBodyWeight` — сама оптимистичная логика (снять снапшот, применить, положить в очередь `SyncEngineService`, откатить снапшот при ошибке) не меняется. Меняется только персистентность (шаг 3).

### 8. Realtime (WS)

`subscribeToRealtimeUpdates()` и хендлеры — без изменений в логике применения патча.

### 9. Снос старого и проверка

Прогнать тесты сервиса, если есть; проверить типы/линт после чистки.

### 10. Согласование с бэком

Формально не требуется (см. research/парный документ) — форма запроса не меняется. Свериться при реализации на случай, если по факту что-то в контракте всё же придётся уточнить.

Любой день вне этого окна (прыжок в календаре на дату из прошлой сессии) после перезагрузки страницы показывался пустым до ответа сети, хотя физически уже лежал в IndexedDB — цель "once seen, forever cached" не выполнялась за пределами стартового окна.

Исправлено: гидрация переведена с одноразового окна на подневную — `hydrateDayFromIndexedDb(dateISO)` вызывается на каждую смену `selectedDayIso$$` (тот же эффект, что и проверка сегментов), перед сетевой проверкой сегмента. Читает один день по ключу (`idbGetDiaryDay`, заменил `idbGetDiaryDayRange` — диапазонное чтение больше не нужно), пропускает чтение, если день уже в памяти, и не перетирает день, если сеть успела ответить раньше. `tsc --noEmit` и `ng build --configuration dev` — чисто.

- ⭕ Ручная проверка: день, ранее посещённый в прошлой сессии и вне стартового окна — после reload и перехода на него виден мгновенно из кэша, без пустого экрана

2026-08-05, второй багфикс: на медленной сети/при быстром пролистывании вернулся сам исходный баг (цепочка запросов) — `pendingSegmentFetches` дедуплицировал только точное совпадение окна по строке, а не "покрыта ли дата". Пока первый запрос летит, `segments` пуст (пополняется в `.then()` после ответа) → каждая новая дата на пути пролистывания читалась как непокрытая → новый несовпадающий по границам запрос на каждый шаг, пока не пришёл первый ответ. Плюс рядом нашёл: сетевая ошибка внутри `getFoodDiaryFullUpdateRange` тихо проглатывалась и всё равно помечала сегмент подтверждённым (`{}` от catch неотличим от "день реально пуст").

Исправлено: добавлен `pendingSegments` — окна, ещё не подтверждённые, но уже в процессе получения. `isDateCovered`/`findContainingSegment` теперь проверяют `segments ∪ pendingSegments` — второй запрос за уже летящий диапазон не стартует. Размер батча (первый ±7 / остальные ±30) теперь тоже считается по `segments ∪ pendingSegments`, а не только по подтверждённым. `getFoodDiaryFullUpdateRange` больше не глотает ошибку — `fetchSegmentAround` ловит её сам и не подтверждает сегмент при отказе (дата останется непокрытой, будет запрошена заново при следующей навигации). `tsc --noEmit` и `ng build --configuration dev` — чисто.

- ⭕ Ручная проверка: быстрое пролистывание/медленная сеть — один запрос на сегмент, без цепочки при незавершённом первом
