# 53 — Выбор продуктов «Истории продукта» в URL

Только фронт (`megaapp-front`). Бэк не меняется (см. «Бэк»), парный план не нужен. Номер 53 занят в обоих репозиториях.

## Цель

- Выбранные в «Истории продукта» продукты отражаются в URL `/food`.
- URL сохраняется закладкой; открытие закладки на десктопе подставляет все продукты → бэк отдаёт историю → фронт рисует таблицу и разбивку графика калорий (план 46).
- Главная платформа — десктоп. Мобилка — только если работает без доп. сложности.
- Вперёд/назад браузера не поддерживаются (сознательно).

## Текущее устройство

- Выбор — root-сервис состояния истории: хранит только id, имена/архив берёт из живого каталога, id вне каталога отсеивает. Лимит 20 (как на бэке).
- Состояние только в памяти: перезагрузка и выход из аккаунта его стирают.
- Загрузка истории запускается явно из добавления/удаления и опирается на отфильтрованный по каталогу список. Фоновая перезагрузка — по изменению дневника.
- Роут `/food` → `FoodScreen` (единственный компонент, живущий ровно пока открыт `/food`). Внутри — колонки (десктоп) или вкладки дневник/статистика (1 колонка); смена вкладок/колонок роут не меняет.
- Query-параметры в приложении нигде не читаются, кроме `returnUrl` в авторизации.
- Каталог: при старте сразу из localStorage, затем с сервера в `loadInitialFoodData`. При пустом кэше (первый вход после логина, очищенное хранилище) каталог пуст до ответа сервера.
- Навигация по меню — `router.navigate` на голый путь → query-параметры уходят при уходе с `/food`.
- `authGuard` кладёт полный URL (с query) в `returnUrl`; форма входа возвращает на него.
- Телеметрия шлёт `router.url` целиком (с query).

## Архитектура

### Формат

- `/food?products=12,45,7` — id продуктов каталога через запятую, в порядке чипов.
- Angular не кодирует запятую в query → URL читаемый.

### Источник истины

- Root-сервис состояния остаётся владельцем выбора.
- URL — проекция состояния на `/food` + однократный вход при открытии экрана.
- Синхронизацию держит `FoodScreen`: только он знает, что открыт `/food`, и живёт ровно столько же.

### URL → состояние (один раз, при создании `FoodScreen`)

- Параметр есть → разбор → выбор заменяется целиком.
- Разбор: целые положительные id, дубли убираются, мусорные токены пропускаются, максимум 20 (лишние отбрасываются).
- Параметр есть, но пустой/весь мусорный → выбор очищается.
- Параметра нет → состояние не трогается (выбор переживает уход с `/food` и возврат через меню).
- Чтение — из снимка маршрута при создании компонента, до первого прогона эффекта записи.

### Состояние → URL (эффект в `FoodScreen`)

- Любое изменение выбора → навигация на тот же маршрут с `replaceUrl` (история браузера не засоряется), параметр заменяется; пустой выбор → параметр удаляется.
- Если строка совпадает с текущей → навигации нет (нет лишних циклов).
- Смена только query не пересоздаёт `FoodScreen` и не перезапускает guards (поведение Angular по умолчанию) → нет перезагрузки данных экрана.
- Возврат на `/food` через меню без параметра: состояние жило в root → эффект сразу дописывает параметр. На `/food` URL всегда совпадает с выбором.

### Загрузка истории не зависит от времени прихода каталога

- Проблема: при пустом кэше каталога выбор из URL сначала ни во что не резолвится → запрос не уходит; после прихода каталога чипы появляются, но история не грузится.
- Решение: загрузка запускается реактивно по набору выбранных продуктов, найденных в каталоге (сравнение по содержимому). Добавление, удаление и замена выбора только меняют состояние, перезагрузку сами не вызывают.
- Один триггер покрывает: правку пользователем, применение URL, поздний каталог.
- Переименование, архивация и прочие правки каталога, которые не меняют набор id, повторного запроса не вызывают.
- Логика переднего/фонового режима и отказ от `resource()` (план 37) не меняются.

### Сырые id против найденных

- В URL пишутся сырые id выбора, не только найденные в каталоге. Иначе пустой на старте каталог стёр бы параметр.
- Неизвестные id (мусор в URL, удалённый продукт) не показываются и не запрашиваются.
- Любая правка выбора пользователем пересобирает список из видимых продуктов → неизвестные id уходят из URL.
- Лимит считается по видимым продуктам, как сейчас. Сырой список не превышает 20: разбор URL режет до 20, правка пересобирает из видимых.

### Края

- Не залогинен → `authGuard` → вход → возврат на полный URL с параметром. Работает без доработок.
- Раздел «Еда» выключен → `isChapterSelected` уводит в настройки, параметр теряется. Приемлемо.
- Выход из аккаунта: состояние уже сбрасывается, редирект на `/auth`.
- Закладка открыта в уже открытой вкладке → полная загрузка страницы → параметр применяется. Переход на `/food?products=…` изнутри приложения не нужен — таких ссылок нет.
- Чужие id (вход под другим пользователем с тем же URL): бэк фильтрует по пользователю, каталог их не знает → пусто, без ошибок.

### Телеметрия

- `router.url` теперь несёт список id → рост кардинальности маршрута и утечка данных выбора в события.
- В телеметрию отдаётся путь без query-строки.

### Мобилка

- Отдельного кода нет: тот же роут, тот же root-сервис, тот же `FoodScreen`. Выбор из URL применяется, история видна на вкладке «Статистика».
- Автопереключение на вкладку статистики — нет (лишняя сложность ради второстепенной платформы).

## Бэк

- Изменения не нужны. `GET /api/food/product-history`:
  - фильтрует по пользователю;
  - лимит 20 совпадает с фронтом;
  - разбор id терпит пробелы и пустые токены.

## Что не делаем

- Синхронизация вперёд/назад браузера.
- Именованные наборы, хранение наборов в localStorage или на сервере.
- Кнопка «скопировать ссылку» (закладка делается средствами браузера).

## Повторный анализ бэка (11.11.2026)

Задача: проверить, нужен ли бэку рефакторинг, если считать, что фича была в проекте с самого начала. Минимум правок целью не был. Вывод: бэк не меняется. Обоснование ниже.

Открытие закладки `/food?products=…` по шагам:

- nginx: `try_files … /index.html` отдаёт SPA на любой путь, query-строка сохраняется. Go в этом не участвует.
- Авторизация и настройки: те же запросы, что при любом открытии `/food`.
- Каталог `GET /api/food/catalogue` общий для всех пользователей и включает архивные продукты. Имя и признак архива для любого id из закладки фронт уже знает.
- Удалить можно только продукт без записей в дневнике. Поэтому у истории не бывает «осиротевших» строк, а удалённый id из закладки даёт пустой ответ.
- `GET /api/food/product-history`:
  - фильтрует по пользователю;
  - сам считает ккал и процент от нормы месяца;
  - лимит 20 совпадает с разбором URL на фронте.
- Фронт после разбора URL никогда не шлёт мусор и больше 20 id. Поэтому ответы 400 в этом сценарии недостижимы.

Варианты, которые рассматривали и отклонили:

- Отдавать вместе с историей имена и признак архива. Это дубль каталога, который в любом случае грузится для дневника, и при переименовании данные бы разъезжались.
- Хранить набор на сервере. Противоречит решению «набор живёт в URL».
- Переименовать `catalogueIds`, сгруппировать ответ по продуктам. Никакой сценарий этого не требует, это перекраска контракта.

## Реализация: уточнения (11.11.2026)

Решения, которые появились при реализации. Старый текст выше остаётся. Здесь — что его уточняет.

- Синхронизация живёт в отдельной функции рядом с сервисом состояния. `FoodScreen` только вызывает её при создании, сам в синхронизации не участвует.
- Запись в URL идёт навигацией роутера с `replaceUrl`, а не через `Location`. Роутер остаётся единственным владельцем URL. Если бы URL менялся мимо роутера, то при отменённой навигации или ошибке загрузки чанка роутер вернул бы URL к своей устаревшей версии, а закладка сохранила бы не тот набор.
- Параметр читается при каждой навигации в `/food`, а не только при создании экрана. Без этого клик по пункту меню «Еда», когда пользователь уже на `/food`, переиспользует компонент и стирает параметр.
- Пока сессия не активна, URL не пишется. При выходе из аккаунта выбор очищается, пока идёт редирект на `/auth`. Навигация отсюда перебила бы этот редирект.
- Свой ответный параметр, который возвращается из роутера, не применяется к выбору. Пока навигация шла, выбор мог измениться.
- Запись выполняется в эффекте, то есть после завершения навигации, которая принесла URL. Вложенной навигации внутри активации маршрута нет.
- Телеметрия: `app.route_ready` записывается только при смене пути. Навигация, которая меняет только query, ничего не перерисовывает, и мерить её незачем.
