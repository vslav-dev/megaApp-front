# 48. Персонализация поиска еды по истории выборов — фронтенд (парный план)

Основной план бэкенда (цель, формула, хранение, затухание, риски): [48-food-search-personalization.implementation-plan.md](../../megaapp-back/plans/48-food-search-personalization.implementation-plan.md). Здесь только работа фронта.

## Задача фронта

Одна: при создании записи дневника из поиска передать серверу текст запроса, по которому найден товар. Остальное — на сервере (ранжирование, история, затухание). Протокол WebSocket поиска не меняется.

## Как сейчас

- Поле поиска — `FoodProductPicker`: на каждый ввод исправляет раскладку, отрезает вес («молоко 200») и вызывает серверный поиск; в легаси-режиме ищет локально по старым названиям.
- Исправленный текст запроса хранит `FoodCatalogueService`; пикер его наружу не отдаёт.
- Выбор товара: клик или Enter по первому → пикер отдаёт товар и вес. Дальше два пути в `FoodSearch`:
  - вес указан в запросе — запись создаётся сразу;
  - иначе открывается форма добавления записи; запись создаётся там по кнопке.
- Третий путь: тот же пикер в режиме «выбрать продукт для истории» — запись дневника не создаётся.
- Создание записи — оптимистичная операция через движок синхронизации; тело операции — сама запись дневника; идемпотентность по `operationId` обеспечивает движок.
- Клиентский кэш выдач: по тексту запроса; ответ сервера, отличающийся от кэша, показывается и обновляет кэш.

## Решение

### Что запоминается
- Запрос = текст, ушедший в серверный поиск: раскладка исправлена, вес отрезан. Берётся у `FoodCatalogueService`, а не пересобирается в пикере, чтобы ключ совпал с серверным посимвольно.
- В легаси-режиме запрос не запоминается: он про старые названия, серверному ранжированию такой запрос не нужен и испортил бы историю.
- Пустой запрос — нет подсказки.

### Путь запроса до создания записи
- Пикер при выборе отдаёт вместе с товаром и весом текст запроса (или отсутствие его).
- Состояние окна добавления хранит запрос выбранного товара рядом с самим товаром и сбрасывает вместе с ним (возврат к поиску, закрытие). Повторный выбор перезаписывает.
- Оба места создания записи передают запрос в сервис дневника: форма добавления (запрос из состояния окна) и быстрый путь с весом (запрос из выбора).
- Сервис дневника кладёт запрос в тело создания **отдельным полем**, не в запись дневника: запись хранится в локальном кэше дня и участвует в слиянии с сервером, запрос там лишний. Нет запроса — поле не добавляется.
- Правка продукта из формы добавления, возврат назад: запрос остаётся с товаром.
- Не передаётся: восстановление удалённого дня, выбор для истории продукта, создание нового продукта «на лету» (в основном плане отложено).

### Клиентский кэш выдач — не трогаем
После выбора сервер может изменить порядок для затронутых запросов. Кэш покажет сохранённый порядок и тут же заменится ответом сервера (механика уже есть, план 43). Порядок поменяется на экране не чаще одного раза на запрос после изменения личных предпочтений; когда предпочтения устоялись, кэш и ответ совпадают, мерцания нет. Версию кэша не меняем. Сброс кэша после выбора отвергнут: он убрал бы мгновенный показ как раз для привычных запросов.

### Метрика эффекта
Телеметрия «позиция выбранного товара»: при создании записи из поиска — номер товара в показанной выдаче и размер выдачи (через уже существующую телеметрию поиска). Нужна, чтобы после выкладки видеть, растёт ли доля первых мест, и подобрать параметры на бэке. Запрос текстом в телеметрию не кладётся, только длина — как в остальных событиях поиска.

## Не меняется

- Мгновенный показ из кэша, задержка отправки 200 мс, исправление раскладки, разбор веса.
- Легаси-поиск.
- Протокол WebSocket, форматы ответов поиска.
- Структура записи дневника на клиенте.

## Порядок выкатки

Сначала бэкенд (понимает новое поле), затем фронт. Обратный порядок тоже безопасен: бэкенд без нового кода игнорирует неизвестное поле тела.

## Проверка

- Сервис дневника: тело создания содержит запрос, если он передан, и не содержит, если нет; запись в локальном кэше дня без запроса.
- Пикер: при выборе отдаёт исправленную раскладку без веса («vjkjrj 200» → «молоко»); в легаси-режиме запроса нет; Enter по первому результату тоже отдаёт запрос.
- Состояние окна добавления: запрос хранится с товаром, сбрасывается при возврате к поиску и закрытии; правка продукта его сохраняет; путь выбора для истории запрос не использует.
- Быстрый путь с весом передаёт запрос; форма добавления передаёт запрос.
- Телеметрия: позиция и размер выдачи при выборе из поиска.
- По `megaapp-front`: `npm run lint` (0 замечаний), `npx tsc --noEmit -p tsconfig.app.json` и `-p tsconfig.spec.json`, `npm test -- --watch=false`.

## Уточнение: запрос — тот, для которого показан список (30.10.2026)

Дополняет раздел «Что запоминается». Запоминается не последний набранный текст, а запрос, ответ на который сейчас на экране. Причина: после нажатия клавиши список ещё ~200 мс и время ответа остаётся от предыдущего запроса; клик по нему не должен записаться под новым набранным текстом.

- Служба поиска каталога хранит запрос рядом с показанной выдачей и обновляет его там же, где обновляется номер показанного запроса (показ из кэша и показ ответа сервера).
- Пикер при выборе отдаёт именно его. Легаси-режим и пустое поле — по-прежнему «нет запроса».
- Остальное без изменений: стирание и промежуточные наборы не отслеживаются, в бэкенд уходит один текст в момент создания записи.

### Чеклист уточнения

- ✅ Служба поиска каталога: запрос показанной выдачи отдельно от последнего набранного
- ✅ Тест: клик по списку предыдущего запроса записывается под ним, а не под новым набранным

## Итоги реализации (30.10.2026)

Отличия от плана:

- **Телеметрия пишется в момент выбора товара в выдаче**, а не при создании записи: позиция известна только там, а запись создаётся позже в форме (или не создаётся вовсе, если пользователь передумал). Событие `food.catalogue_pick`: позиция товара, размер выдачи, длина запроса; длительность — время от показа списка до клика. Пишется и при выборе товара для истории продукта (тот же пикер).
- **Запрос показанной выдачи хранится в службе поиска каталога** и обновляется в единственном месте показа выдачи (из кэша и из ответа сервера). Метод `pickProduct` возвращает его и пишет телеметрию.
- Добавлены тесты компонентов `FoodSearch` и `DiaryEntryAddForm` (рендер с подменёнными службами; счётчик «катящихся» чисел заменён заглушкой, потому что jsdom не умеет измерять текстовые диапазоны).

## Проверка успеха после выкладки (30.10.2026)

Событие телеметрии `food.catalogue_pick` (позиция выбранного товара, размер выдачи, длина запроса, время до выбора) собирается для оценки фичи. Через неделю после выкладки по нему проверяется успех и подбираются коэффициенты на бэкенде; что смотреть и что подбирать — в разделе «Проверка успеха и настройка коэффициентов после выкладки» [плана бэкенда](../../megaapp-back/plans/48-food-search-personalization.implementation-plan.md). Известный шум в событии (находка 2 ревью бэкенда): оно пишется и при выборе продукта для истории, позиция 0 означает «товара нет в выдаче».
