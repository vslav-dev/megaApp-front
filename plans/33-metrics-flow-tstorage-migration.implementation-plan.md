# 33. Metrics flow: ring buffer вместо session-wide карты — megaapp-front

Часть кросс-репо миграции metrics-flow на tstorage-архитектуру: [flatline:07-research](../../../flatline/plans/07-metrics-flow-performance.refactoring-research.md) (§5 приложения), [flatline:07-implementation-plan](../../../flatline/plans/07-metrics-flow-tstorage-migration.implementation-plan.md) (хранилище + бинарный формат), [back:33](../../megaapp-back/plans/33-metrics-flow-tstorage-migration.implementation-plan.md) (передача формата дальше во фронт). Этот план — последний в цепочке, реализует клиентскую часть.

## 0. Рамки

- Меняется: приём/хранение/рендер точек метрик (`metrics.service.ts`, `metrics-dashboard.ts`, `metrics-series.ts`, `metric-chart-card.ts`).
- **Не меняется**: `performance-metrics.service.ts` (собственная perf-телеметрия) — отдельная проблема (research-док A4), не трогаем в этом плане.
- **Не в объёме**: A5 (сузить `serviceMetricsData$$` до открытой панели) из research-дока формально поглощается этим планом — новая ring-buffer модель структурно не позволяет держать данные вне видимой панели, отдельно делать не нужно (§2.2).

## 1. Текущая реализация (для справки)

- `pointsByKey: Map<string, MetricPoint>` (`metrics.service.ts`) — единая карта на всю сессию, ключ `granularity:service:name:bucket`, растёт, пока не сработает `prunePoints` (полный обход всей карты на каждый merge) по возрастному окну (`CACHE_WINDOW_SECONDS`: 48ч/30д/365д), не по тому, что реально открыто.
- `publishPoints` — полная пересортировка всего накопленного набора на каждый merge (REST-ответ или WS-тик), публикация в `points$$`.
- `serviceMetricsData$$` (`metrics-dashboard.ts`) — computed, строит карточки по всем ~284 метрикам/8 сервисам статического каталога независимо от открытой панели, пересчитывается на каждое изменение `points$$`.
- `MinuteMetricCollapseCache` (`metrics-series.ts`) — уже инкрементальный (add/remove по краям окна), полный rebuild только при разрыве непрерывности или смене конфига — эта часть логики концептуально близка к ring buffer уже сегодня, переиспользуется, не переписывается с нуля.
- IndexedDB (`idb-cache.ts`/`indexed-db-cache.service.ts`) — весь `pointsByKey` целиком сериализуется в один `kv`-ключ на каждый debounced write (1с).

## 2. Целевая архитектура

### 2.1. Ring buffer вместо `Map` на всю сессию

Вместо одной карты, копящей все когда-либо увиденные за сессию точки по всем метрикам, на которые клиент хоть раз подписывался — по одному кольцевому буферу фиксированной ёмкости **на каждую реально смонтированную (видимую) серию** `(service, metricName, granularity)`. Вставка новой точки O(1) с автоматическим вытеснением старой, без отдельного прохода `prunePoints` и без пересортировки.

**Адресация — по bucket'у, не по порядку вставки.** Позиция слота = `(bucket / step) % capacity` (тот же принцип, что у ring buffer хранилища на бэке, [flatline:07 §1](../../../flatline/plans/07-metrics-flow-tstorage-migration.implementation-plan.md)), и в слоте хранится не только `value`, но и сам `bucket`, которому оно принадлежит. Чтение сверяет: bucket в слоте совпадает с ожидаемым для этой позиции — если нет (слот никогда не заполнялся, либо там осталось значение из предыдущего оборота кольца, устаревшее на целую ёмкость), слот читается как «нет данных», график рисует разрыв — так же, как сегодняшний sparse-series рендер (`buildSparseLineSeries`), только проверка теперь на уровне буфера. Это защищает от алиасинга: без сверки bucket'а старое значение из позапрошлого оборота кольца могло бы попасть на экран как будто оно свежее, после длинного разрыва в данных.

**Ёмкость — фиксированное число точек, не «сессионное окно»**: minute = **1440** (1 день — ровно то, что физически показывается на этой гранулярности; ретеншен на Flatline/back остаётся 2880/48ч, см. [flatline:07 §1.1](../../../flatline/plans/07-metrics-flow-tstorage-migration.implementation-plan.md) — фронт просто никогда не запрашивает и не хранит больше 1440 из них). hour/day — ёмкость равна сегодняшнему `CACHE_WINDOW_SECONDS` в точках (720/365), не меняется.

Буфер создаётся при монтировании графика (открытии панели/карточки) и **гидратируется из IndexedDB** (§2.4) синхронно с открытием. При размонтировании — не выбрасывается молча: перед уничтожением RAM-копии состояние буфера **сбрасывается (flush) в IndexedDB** (см. §2.4 — иначе при следующем открытии этого сервиса пришлось бы ждать полный REST-ответ вместо мгновенного показа кэша).

### 2.2. `serviceMetricsData$$` — узкий по построению, не по фильтру

Сегодняшний computed строит карточки для всего статического каталога и полагается на `expandedPanel$$` только для того, что рендерится в шаблоне (research-док §2.4/§1.3 п.6). В новой модели данных для метрик вне открытой панели просто не существует в буферах — значит, computed физически не может построить carousel-данные для того, чего нет. `serviceMetricsData$$` перестраивается так, чтобы явно принимать текущий scope (`expandedPanel$$`/`metricsScope$$`, уже существующие сигналы) как источник, по которому создаются/используются буферы — full-catalog итерация уходит целиком, не только для видимых панелей, а структурно. Это закрывает A5 research-дока как побочный эффект архитектуры, не отдельной оптимизацией.

Для health-dot/summary-виджетов, которым нужно «последнее значение по каждой метрике сервиса» **без** полной истории (`metrics-health.service.ts`, использует `METRICS_LATEST`, не `points$$`) — эта часть продолжает работать без единого изменения: она не завязана на `pointsByKey`/ring buffer вообще уже сегодня (research-док §1.3 п.6: `METRICS_LATEST` не трогает `pointsByKey`). Этот пункт объясняет, почему health-dot'ы **не входят** в объём миграции, а не то, что они перестают работать.

### 2.3. Приём бинарного формата

REST-ответ `/api/metrics/history` и WS-сообщения `METRICS_UPDATE`/`METRICS_LATEST` приходят в бинарном формате (back:33 §2.1/§2.3) вместо JSON. Разбор — маленький декодер, читающий заголовок (идентификаторы серий) и заполняющий typed array (`Float64Array`/аналог) напрямую из `ArrayBuffer` полученного сообщения, без промежуточного JS-объекта на каждую точку. Это тот самый «один маленький неизбежный переход» из research-дока §5 — decode здесь настоящий (нельзя, как back на `/history`, просто прокинуть байты дальше — фронту нужны реальные числа для Chart.js), но дешевле JSON.parse и не создаёт объект на каждую точку.

### 2.4. IndexedDB — per-серийная персистентность, живёт дольше самого буфера

Каждая серия `(service, metricName, granularity)` персистится в IndexedDB отдельной записью: тот же bucket-адресованный набор слотов, что и live-буфер (§2.1), той же фиксированной ёмкости — IndexedDB никогда не хранит больше, чем помещается в буфер при следующей гидратации (не «храним всё, потом отбрасываем лишнее при чтении», а «лишнее никогда не пишем»).

Персистентность **не привязана к тому, смонтирован ли график прямо сейчас**. При размонтировании live-буфер финально сбрасывается в IndexedDB перед уничтожением RAM-копии, а не выбрасывается вместе с ней. При повторном открытии сервиса, не бывшего на экране какое-то время, буфер сначала **гидратируется из IndexedDB** — мгновенно, синхронно с открытием панели: это и даёт эффект «часть графика видна сразу». Следом уходит REST-запрос по текущим `historyCheckedThrough`-курсорам за тем, что накопилось с последнего визита, и пришедшие точки просто дозаписываются в уже гидратированный буфер по своим bucket-позициям — визуально это «дозаполнение через пару секунд». Поведение сохраняется 1:1 относительно сегодняшнего, меняется только источник — конкретная запись per-серии вместо одного блоба на весь `pointsByKey`.

**Важно во избежание путаницы**: гидратация из IndexedDB — это копирование, не перемещение; запись в IndexedDB после чтения никуда не исчезает. Дебounce-writer (1с, коалесcing, не меняется относительно сегодняшнего) пишет в IndexedDB **непрерывно, пока панель открыта** — на каждое живое обновление буфера, а не только в момент закрытия. Flush при размонтировании (см. §2.1) — это не единственная точка записи, а гарантия «добить последний тик», если панель закрыли внутри той секунды, что дебounce ещё не успел сработать сам. Пишет typed array конкретной серии вместо `JSON.stringify` всего `pointsByKey`. `historyCheckedThrough`-курсоры (per-metric watermark'и) остаются как есть.

**Разрыв в сети/долгое отсутствие**: ничего не выбрасывается по таймеру и не ждётся отдельного события очистки. REST/WS всегда присылают только *дельту* с курсора (как и сегодня — не «кольцо целиком»), пришедшие точки просто переписывают свои bucket-слоты. Если разрыв был длиннее ёмкости буфера (для minute — больше суток), самые старые слоты, которые дельта не переписала, при следующем чтении не пройдут сверку bucket'а (§2.1) и читаются как «нет данных» — график покажет разрыв. Активно ничего выбрасывать не нужно, устаревание обнаруживается лениво, в момент чтения.

### 2.5. `forceRefresh`/`clearCache`/heartbeat — поведение не меняется

Разница между форс-рефрешем (сброс курсора → полная глубина ретеншена) и обычным heartbeat-рефрешем (инкрементальная докачка по курсору) — не архитектурная деталь хранения точек, не меняется.

**Периодической автоочистки кэша нет — ни сегодня, ни в новой модели.** Heartbeat (раз в 60с) только дозапрашивает дельту по курсорам, ничего не стирает — это уже так сегодня и не пересматривается. `clearCache()` остаётся единственным путём очистки — ручное/явное действие (не таймер): в новой модели обнуляет активные ring-буферы (сброс слотов) и удаляет их персистентные копии в IndexedDB (§2.4), сбрасывает `historyCheckedThrough`-курсоры, затем как и сегодня сразу вызывает `refreshHistory()` — та же форма, что сейчас, просто оперирует буферами вместо `Map`.

### 2.6. `MinuteMetricCollapseCache` — адаптация, не переписывание

Инкрементальная логика (`canIncrementallyUpdate`, add/remove по краям окна, полный `rebuild()` только при разрыве непрерывности) уже структурно соответствует духу ring buffer — меняется источник (`rawPoints: MetricPoint[]` → typed-array буфер), не алгоритм сдвига окна.

## 3. Что не меняется — явно

- `performance-metrics.service.ts` — не трогаем (см. §0).
- `metrics-catalog.ts` и per-service каталоги — статические определения, не зависят от формата хранения точек.
- `metrics-settings.service.ts`, `metric-card-expansion.service.ts` — UI-настройки, не про данные.
- Различие manual force-refresh vs. automatic heartbeat (уведомления, backoff, `retryAfterMs`) — не про формат, не меняется.
