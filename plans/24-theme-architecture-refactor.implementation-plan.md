# 24. Рефакторинг архитектуры темы

## Описание

Изначальный запрос — рассинхрон анимации при смене темы (часть UI меняет цвет мгновенно, часть — с разной скоростью). Разбор показал, что это симптом более широкой проблемы: управление цветом/темой в приложении собиралось разрозненно, "где возникла мысль — там и вставили", без единой архитектуры. План закрывает это целиком, тремя направлениями:

1. **Единая длительность цветового перехода на момент смены темы** — сейчас у каждого компонента своя (125/180/200/250ms, часть — без анимации вообще).
2. **Устранение дублирования тёмного/светлого варианта на уровне CSS** — решение "как посчитать цвет в тёмной теме" сейчас продублировано вручную в десятках мест внутри отдельных компонентов, вместо одного места.
3. **Централизация темизации графиков (Chart.js)** — три домена (деньги/еда/метрики) сейчас независимо друг от друга решают, какой цвет сетки/текста/линии показать в тёмной теме; в одном месте (метрики) тёмный вариант вообще никогда не был сделан.

Направления независимы друг от друга по риску (можно делать по очереди, в любом порядке), но объединены одной целью — после рефакторинга должно быть одно место, где хранится "что означает тёмная/светлая тема", а не N разрозненных.

## Направление 1 — единая длительность цветового transition

### Текущая реализация

Смена темы (`.dark` на `documentElement`) меняет значения CSS-переменных цвета мгновенно. Компоненты, которые их потребляют, анимируют переход каждый со своей длительностью — отсюда рассинхрон.

### Механизм (согласован)

- Каждый компонент, где сейчас длительность цветового transition задаётся напрямую (литералом или собственной локальной переменной), получает дополнительный уровень: локальная переменная берёт значение из общего "переключательного" токена, если он задан, и только при его отсутствии — падает на свой обычный дефолт.
- Общий токен по умолчанию нигде не установлен → в обычное время ничего не меняется, hover/active/focus-тайминги каждого компонента остаются как есть.
- В момент клика по переключателю темы сервис настроек на короткое, точно совпадающее с длительностью окно выставляет общий токен на `documentElement`, переключает класс темы, затем (по таймеру на ту же длительность) токен убирает.
- Приём — прямое развитие уже существующего в кодовой базе паттерна временного глобального оверрайда transition (`v-expand` уже делает нечто похожее для отключения анимации высоты), только вместо "выключить" — "выставить одну длительность на всех".

### Анализ

Компоненты UI-кита делятся на три группы по текущему состоянию:

1. **Уже используют свою локальную duration-переменную** (кнопка, чекбокс, карточка, инпут) — добавить второй уровень (глобальный токен как приоритетный источник, локальное значение как fallback).
2. **Используют единый транзишн-токен outline-цвета**, общий сразу для многих компонентов (tooltip, color-picker, input, card, checkbox, button, wheel-input) — одно изменение в общем месте закрывает весь этот набор.
3. **Используют общие анимационные токены, которые одновременно обслуживают и цвет, и чисто функциональные (не цветовые) переходы** (v-expand — фон; v-wheel-select и v-dropdown — фон/цвет). Эти токены используются также для transform/opacity в других местах, поэтому цветовую часть отделяем на новый механизм, функциональную анимацию не трогаем.

Отдельно — фон и текст `html`/`body`/корневого контейнера темы сейчас **не анимируются вовсе** (transition не объявлен). Добавляем им transition на новом механизме — это самая заметная поверхность (фон всей страницы).

Точечное исключение — анимация появления/исчезновения самой галочки чекбокса (масштаб + прозрачность иконки): это анимация состояния "отмечено/не отмечено", а не цвета темы, общий токен её трогать не должен.

### Риски

- Если в момент клика по теме элемент в разгаре hover/active-перехода — скорость этого перехода на лету сменится на "тематическую". Редкое совпадение, визуально не критично.
- Общий токен должен быть выставлен **до** переключения класса темы.
- Таймер снятия токена должен точно соответствовать выбранной длительности.

## Направление 2 — устранение дублирования тёмного/светлого варианта в CSS

### Текущая реализация

Помимо центральной точки (переопределение `--v-color-*` под `.dark` в одном файле — это уже сделано правильно), внутри отдельных компонентов встречается **своя собственная** ручная логика "как эта тема выглядит":

- `v-button.css` — порядка 15 повторяющихся блоков вида "в тёмной теме подмешивай белый вместо чёрного при наведении/нажатии", по одному на каждую комбинацию цвет×стиль кнопки — одно и то же решение задублировано вручную на каждом варианте вместо одной точки. То же, в меньшем масштабе, в `v-checkbox.css`.
- `v-slider.css`, `v-toast.css` — цвет тени задан напрямую (буквальным rgba), мимо уже существующих общих переменных цвета тени — тема на эти тени не влияет вообще, хотя механизм для этого уже есть и используется другими компонентами.
- Общие токены внешней тени в файле стилей — заданы один раз и **не переопределены** под тёмную тему вообще (хотя всё остальное в этом файле следует схеме "светлый/тёмный вариант"), из-за чего внешние тени всегда выглядят как в светлой теме.
- 3 места в шаблонах приложения используют цветовые классы Tailwind напрямую, мимо дизайн-системы — единственные точки, где тема не проходит через общие переменные.

### Анализ

Общая проблема во всех этих местах одна: значение "чем контрастировать/куда сдвигать цвет в тёмной теме" вычисляется индивидуально в каждом месте использования, вместо того чтобы быть посчитанным один раз и лежать в переменной, которую все точки использования просто читают. Централизация здесь — не добавление нового поведения, а перенос уже принятых дизайнерских решений в одно место:

- Значение "к какому цвету подмешивать при наведении/нажатии в текущей теме" — становится одной переменной темы (пересчитывается в той же точке, где уже пересчитываются остальные цвета темы), кнопка и чекбокс перестают сами решать, какая сейчас тема.
- Тени, которые сейчас заданы напрямую, переводятся на использование уже существующих общих переменных цвета тени — ровно так, как это уже сделано у других компонентов.
- Общие токены внешней тени получают тёмный вариант в том же файле, рядом с остальными переопределениями под тёмную тему, а не отдельно.
- Три места с прямыми классами Tailwind переводятся на переменные дизайн-системы — по составу изменений это точечная правка трёх шаблонов, не архитектурная работа.

### Чеклист

- ✅ Введена переменная `--v-color-contrast` (чёрный в светлой теме / белый в тёмной), в `flat-blue.css` рядом с остальными цветами темы
- ✅ `v-button.css` — все 9 повторяющихся `:host-context(.dark)`-блоков удалены, база использует `var(--v-color-contrast)`; заодно найдены и удалены 2 полностью мёртвых dark-блока без какой-либо разницы со светлой темой (задваивали одно и то же значение — vestige от прошлой правки)
- ✅ `v-checkbox.css` — 2 блока переведены на переменную; третий (`thumb` → `currentColor`) сознательно оставлен — это не контраст-дублирование, а самостоятельное дизайн-решение для тёмной темы

- ✅ Токены внешней тени (`--v-shadow-outer-1/2`, `--v-bar-shadow-inset/raised`) — переведены на `--v-shadow-color-dark(-strong)` с сохранением исходных значений в светлой теме; заодно удалены как мёртвый код 5 неиспользуемых нигде токенов с той же нетемизированной проблемой (`--v-shadow-outer-0`, `--v-shadow-inset-2/3`, `--v-slider-thumb-shadow*` — три отдельных, никем не потребляемых токена)
- ✅ 3 шаблона с прямыми классами Tailwind — переведены на переменные дизайн-системы (`border-[var(--v-color-border-subtle)]`, danger-баннер — на `color-mix` с `--v-color-danger`, аналогично паттерну в `v-toast`)
- ⭕ Ручная проверка в браузере — визуальная сверка на стороне пользователя

## Направление 3 — централизация темизации графиков

### Текущая реализация

Все фабрики конфигураций графиков (деньги/еда/метрики) уже физически лежат в одном файле, но именно поэтому особенно заметно, что общая часть у них не переиспользуется, а каждая написана с нуля:

- У части графиков цвет сетки и текста берётся из параметра с готовым набором цветов на тему (уже правильно, домен "еда"), у части графиков сетка вообще не задана и остаётся дефолтной серой из библиотеки графиков (не имеет отношения к теме вообще, домен "деньги"), у части — сетка задана буквальным чёрным цветом с прозрачностью, тёмного варианта нет вообще (домен "метрики" — сетка спарклайнов/баров, наш подтверждённый пробел).
- Выбор набора цветов на тему для двух графиков (деньги/еда) продублирован независимо в двух местах — каждый компонент сам читает состояние темы и сам решает.
- При этом почти всё остальное содержимое конфигурации (отключение встроенной анимации библиотеки — раз пересоздаём график сами, растягивание на контейнер, поведение легенды/тултипа) у графиков одинаковое, отличается только само визуальное — цвет линий/баров конкретного домена и форматирование чисел в тултипе.

### Анализ

Задача — выделить общую, не зависящую от домена часть конфигурации графика (тема-зависимые цвета сетки/текста/легенды + одинаковые для всех структурные настройки) в одно общее место, из которого её берут все шесть точек создания графиков. Каждый график поверх общей части добавляет только то, что реально уникально для него — цвета своих датасетов и специфичное форматирование тултипа/оси. Выбор набора цветов на тему при этом тоже читается один раз в общем месте, а не в каждом компоненте-потребителе отдельно.

Отдельно закрывается подтверждённый пробел: сетка спарклайнов/баров метрик получает тёмный вариант наравне с остальными графиками — как часть перехода на общую тема-зависимую часть конфигурации, а не отдельным патчем поверх старой структуры.

## Явно вне рамок

- Canvas-графики — плавность самого перехода цвета датасетов между темами (кроме сетки/текста — см. направление 3) не делаем: Chart.js перерисовывает canvas целиком, CSS-transition к нему неприменим, а встроенная анимация библиотеки на других этапах сознательно отключена (см. код) — не расширяем.
- Цвет scrollbar — анимируемость зависит от браузера, не гарантируем результат.
- Категориальные палитры (цвета счетов, категорий трат/доходов) — сознательно не завязаны на тему, это цвет-идентификатор данных, а не элемент темы, трогать не нужно.
