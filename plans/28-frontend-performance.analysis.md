# 28. Анализ production-логов производительности фронтенда (07–17 авг 2026)

Этап 1 плана [25-frontend-ux-performance-measurement](25-frontend-ux-performance-measurement.implementation-plan.md) («Собрать логи неделю» → «Свести результаты, выбрать места второго этапа»). Только анализ данных. Рефакторинг/оптимизации — отдельный документ, следующий шаг.

Каждая операция ниже разобрана по длительности самой по себе — независимо от того, сколько раз она сработала за 10 дней. Редкая операция (единицы-десятки срабатываний в день) чинится с тем же приоритетом, что и частая: количество вызовов не определяет важность.

## TL;DR — главные находки по длительности

- **`money.snapshot_apply` (открытие `/money`): p50 = 7999 мс, p95 = 15173 мс.** Каждое открытие денег типично ждёт сервер 8–15 секунд при 16 счетах / ~4090 транзакциях.
- **`food.initial_load`/`food.screen_ready`/`food.diary_segment_load`/`food.stats_response_apply` (открытие `/food`): p50 ≈ 3000–4800 мс**, и это **одинаково** на desktop/mobile/tablet — разброс между платформами единицы процентов, не разы. Слабое мобильное железо — не причина; общий множитель одинаков для всех устройств.
- **`food.catalogue_load`: p50 ≈ 3000 мс** независимо от платформы и от того, откуда взяты данные (`cache`/`server`). Каталог не растёт (стабильно 468 записей) — похоже на фиксированную стоимость самого вызова, а не на объём данных.
- **`metrics.history_refresh`: p90 = 28785 мс, p95 = 45066 мс** (без учёта многочасовых выбросов — см. ниже) — тяжёлая операция каждый раз, когда срабатывает.
- **`metrics.cache_hydrate` (гидратация кэша на холодном старте): p95 = 11292 мс, max = 30722 мс.**
- **`app.route_ready` на `/metrics`: p95 = 6591 мс, max = 27095 мс** — переход на страницу иногда занимает до получаса ощущения зависания.
- **Многочасовые выбросы** (`metrics.history_refresh` до 4 468 009 мс = 74.5 мин, `food.initial_load` до 1 539 705 мс = 25.6 мин) — во всех случаях `renderMs ≈ elapsedMs`, то есть почти всё время ушло между «данные готовы» и отрисовкой (два `requestAnimationFrame`), а rAF не тикает в свёрнутой вкладке. Это методологический артефакт замера (фоновая/уснувшая вкладка), не реальное ожидание пользователя. Разобрано в §5.
- **Сборщик телеметрии сам по себе неэффективен**: `PerformanceMetricsService.record()` → `trimQueue()` делает `JSON.stringify(this.queue)` целиком на **каждый** вызов, чтобы сверить лимит 1 MiB очереди. Это архитектурная стоимость самого механизма записи, не зависящая от частоты конкретной операции — при высокочастотных источниках (realtime-обновления графиков) она складывается в постоянную нагрузку на главный поток. Косвенное подтверждение — 825 527 событий потеряно на клиенте за 10 дней из-за переполнения этой же очереди (`queueDroppedBeforeBatch`).
- **Долгие задачи главного потока (`app.long_task`) тяжелее всего на `/metrics`** (p95=703мс, max=9726мс), **чаще всего — на `/food`** (4386 событий, p95=287мс). `/money` заметно легче обоих направлений.
- **Инструментация не покрывает мутации** (`money.mutation`, `food.diary_mutation`, `food.catalogue_mutation`), фото/голосовой ввод (`food.photo_flow`, `food.voice_flow`) и холодный старт (`app.bootstrap`) — самые ощутимые для пользователя операции (добавить запись, сфотографировать еду, открыть приложение с нуля) вообще не измерены, хотя мутации точно происходили (см. §7).

### Схема записи (для справки)

```typescript
interface PerformanceMetricRecord {
  eventId: string; timestampMs: number; sessionId: string;
  operation: string; elapsedMs: number; renderMs?: number;
  route: string; outcome: 'success' | 'error';
  attributes?: Record<string, string | number | boolean>;
  device: { platform: 'mobile'|'tablet'|'desktop'; mobileDevice; mobileScreen;
    viewportWidth; viewportHeight; screenWidth; screenHeight; dpr; touchPoints;
    hardwareConcurrency?; deviceMemory?; connectionType?; connectionRtt?; userAgent };
}
```

Бэкенд (`internal/ws/performance_metrics.go:245-249`) дописывает `receivedAt`, `userId`, `clientId`, и на первой записи батча — `queueDroppedBeforeBatch`, если клиент терял события из-за переполнения очереди.

### Как читать `elapsedMs` / `renderMs`

- `elapsedMs` = `performance.now()` от старта операции до её завершения. Для `measureAsync` — включает сетевое ожидание.
- `renderMs` (только у части операций, через `recordAfterPaint`) = время от готовых данных до **двух** `requestAnimationFrame` подряд — цена именно отрисовки/интерфейса.
- **Важно**: `requestAnimationFrame` не тикает в свёрнутой/неактивной вкладке. Если пользователь свернул вкладку между стартом и концом измерения, `elapsedMs`/`renderMs` включают всё время простоя — вплоть до часов. Разобрано отдельно в §5.
- Полный каталог операций и что каждая измеряет — в [25-frontend-ux-performance-measurement.implementation-plan.md](25-frontend-ux-performance-measurement.implementation-plan.md#метрики--полный-набор-верхнеуровневых-flows).

## 2. Методология анализа

Инструмент: read-only Python-скрипт (stdlib, venv `python3.12.8`, без внешних зависимостей), потоково построчно читает все 4 файла, для каждой операции строит точную гистограмму `elapsedMs`/`renderMs` (`Counter[int, int]`) — это даёт **точные**, не приближённые перцентили (метод nearest-rank), а не выборочную оценку. Разрезы: по операции, платформе, маршруту, календарному дню (UTC по `receivedAt`), и по «размерным» атрибутам (`days`, `entries`, `points`, `transactions` и т.п. — где стоимость операции потенциально зависит от объёма данных). Отдельно — top-20 самых медленных событий по ключевым операциям и top-30 глобально, для качественного разбора выбросов.

Полный проход по всем 5.73М записей: **47 секунд**, пиковая память — низкая (гистограммы, не сырые списки). Скрипт ничего не пишет на диск, только печатает JSON-отчёт в stdout.

Часть API устройства (`connectionType`, `connectionRtt`, `deviceMemory`, `app.long_task`) браузер-специфична: Network Information API и Long Tasks API поддержаны не во всех браузерах, участвовавших в сборе. Это ограничивает то, что можно сказать про сеть/long-task конкретно для сессий на непокрытых браузерах — см. §10.

## 5. Многочасовые выбросы — методологический артефакт, не реальное ожидание

Самые большие значения `elapsedMs` в датасете:

| elapsedMs | renderMs | Operation | День | Комментарий |
| ---: | ---: | --- | --- | --- |
| 4 468 009 (74.5 мин) | 4 467 494 | `metrics.history_refresh` | 12.08 | `renderMs≈elapsedMs` |
| 3 622 056 (60.4 мин) | 3 621 704 | `metrics.history_refresh` | 08.08 | `renderMs≈elapsedMs` |
| 2 546 499 (42.4 мин) | 2 545 283 | `metrics.history_refresh` | 16.08 | `renderMs≈elapsedMs` |
| 1 539 705 (25.6 мин) | 1 537 269 | `food.initial_load` | 11.08 | `renderMs≈elapsedMs` |
| 309 965 (5.2 мин) | 300 388 | `food.initial_load`/`screen_ready`/`diary_segment_load` (одна сессия) | 14.08 | `renderMs≈elapsedMs` |

Во всех случаях почти всё время уходит между «данные готовы» и «два кадра отрисовки» (`recordAfterPaint`, двойной `requestAnimationFrame`), а rAF не тикает в свёрнутой/неактивной вкладке. Это значит: операция стартовала, пользователь свернул вкладку или система ушла в сон, и таймер продолжал тикать до возврата — часы «ожидания» не были реальным ожиданием перед экраном.

Это не повод отбросить операцию как «нерепрезентативную» — `history_refresh` и `food.initial_load` всё равно объективно медленные операции даже без этих значений (см. §4, §6). Но при подсчёте p99/max по ним эти конкретные точки стоит понимать правильно, а не как «пользователь ждал час». На 2-м этапе стоит добавить в замер флаг `document.visibilityState` на старте/финише операции, чтобы отделять такие случаи автоматически, а не вручную по совпадению `renderMs≈elapsedMs`.

`money.snapshot_apply` (`source: server`, 16 счетов, ~4090 транзакций) — **медиана 8 секунд**, минимум в датасете 8024мс — то есть это типичное поведение при холодном/серверном снапшоте, не редкий выброс. `money.screen_ready` резко бимодален: p50=306 (кэш есть) против p90=9883 (кэша нет, ждём сервер) — амплитуда почти в 30×. Остальные money-операции (`monthly_buckets`, `position_lots`, `*_model`, `*_chart_render`) — все от долей мс до десятков мс, клиентские вычисления не проблема и здесь.

Замечание: `money.snapshot_apply`/`money.screen_ready` подтверждают изменение числа транзакций (4084→4093) за период — значит мутации происходили, хотя телеметрии по ним нет (см. §8).

## 10. Ограничения анализа

- Часть браузеров, участвовавших в сборе, не поддерживает Long Tasks API и Network Information API — для сессий на таких браузерах `app.long_task`, `connectionType`, `connectionRtt`, `deviceMemory` не приходят вообще (не «зависаний не было», а «API недоступен»). Для полной картины по главному потоку на непокрытых браузерах ориентироваться нужно на `app.interaction_delay`, который поддержан шире.
- По `/food` и `/money` абсолютное число событий за 10 дней — низкое (десятки–сотни на операцию), доверительные интервалы у перцентилей широкие; выводы по этим маршрутам менее статистически устойчивы, чем по `/metrics`.
- Мутации, фото/голосовой ввод, холодный старт — не инструментированы, соответствующие жалобы пользователя не проверяемы по текущим логам (см. §8).
- Экстремальные выбросы `elapsedMs`/`renderMs` (сотни тысяч – миллионы мс) отфильтрованы качественно (по совпадению `renderMs≈elapsedMs`), не автоматически — см. §5.
