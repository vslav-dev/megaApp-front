# Рефакторинг архитектуры синка (оптимистичное сохранение + локальный кэш + realtime)

Парный документ: `megaapp-back/plans/15-sync-architecture-refactor.implementation-plan.md`.
Связанный последующий план: `megaapp-back/plans/16-sqlite-read-write-pool-split.implementation-plan.md` (зависит от этого).

## Что делаем и зачем

Триггер: баг «сохранил → зелёный успех → рефреш → на несколько секунд старое значение → само выправилось». Корень — не «не пишется в кэш», а гонка: локальный кэш и оптимистичное состояние ничем не защищены от безусловной перезаписи ответом polling/realtime, который может нести ещё не закоммиченные на бэке данные. Усугубляется тем, что единственное соединение к БД теперь дополнительно контендится опросом метрик.

Точечный фикс (расширить пул чтения к БД) не решает системную проблему: механизм синка разросся, продублирован по доменам, не имеет понятия «версия/свежесть» и не переживает часть неудачных сценариев. Цель — не патч, а пересборка архитектуры: просто, предсказуемо, единообразно для всех доменов.

**Жёсткое ограничение**: пользовательский контракт не меняется. Действие сохраняется мгновенно и оптимистично, откат — только по ошибке, всегда с уведомлением (успех/ошибка). Новая архитектура пользователю не должна быть заметна — кроме исчезновения бага.

## Текущая реализация (обзор)

- Три домена (еда, деньги, настройки) используют общий по духу, но независимо реализованный паттерн: сигнал состояния → мгновенная запись в кэш → очередь фоновой синхронизации.
- Очередь синхронизации: строго последовательная (одна операция за раз), только в памяти, ретраи не идемпотентны по конструкции — для одной операции (правка веса в дневнике) идемпотентность закрыта точечным бэкенд-фиксом (сравнение дельты внутри транзакции), для остальных операций (создание, удаление, восстановление дня) — нет, это зафиксировано как известное ограничение в соседнем плане.
- Realtime — один общий WebSocket-хаб без маршрутизации по типу/домену: лёгкие доменные уведомления (правка записи дневника) и тяжёлая, регулярная нагрузка метрик идут через один канал, один поток сообщений, без приоритета.
- Хидрация при загрузке: кэш применяется мгновенно и синхронно, следом — независимо друг от друга — два асинхронных триггера (обычная загрузка экрана + реакция на статус синка от сокета) перезатирают то же состояние без проверки версии/свежести. Кто ответил последним — тот и выиграл.
- БД: одно соединение на всё приложение, которое исторически совмещает две разные роли — ограничитель производительности и неявный примитив сериализации, используемый как защита от гонок при редактировании записи дневника.

## Ключевые архитектурные проблемы

1. Нет понятия версии/свежести данных ни у одной сущности — неоткуда взять правило «чей ответ актуальнее».
2. Механизм синка реализован трижды с расхождениями и неполным охватом (часть операций денег вообще идёт мимо очереди, без ретраев и отката).
3. Очередь не переживает перезагрузку страницы — закрытие вкладки во время висящей операции навсегда расходит клиента и сервер без пути восстановления.
4. Единственное соединение к БД одновременно и ограничитель производительности, и неявная защита идемпотентности — трогать одно, не сломав другое, рискованно (что чуть не произошло с точечным фиксом).
5. Realtime смешивает несвязанные по частоте/весу домены в одном потоке без маршрутизации и приоритета.
6. Идемпotентность ретраев закрыта точечно под одну операцию, не масштабируется на остальные — уже отмечено как ограничение в соседнем плане.

## Направление рефакторинга (анализ подхода)

- **Версия/свежесть на сущности.** Каждая изменяемая запись несёт признак версии или времени последнего изменения, возвращаемый в любом ответе — HTTP и realtime. Клиент решает «применить или отбросить как устаревшее» по этому признаку, а не по факту получения ответа. Закрывает и баг с рефрешем, и соседний известный кейс «протухший ретрай поверх более новой правки».
- **Один общий механизм синка вместо трёх, с двумя режимами применения.** Формально описанный жизненный цикл операции — поставить в очередь → подтвердить/откатить с уведомлением — которым домены только параметризуются (сущность, запрос, что откатывать). Обязательное требование: движок одинаково поддерживает **optimistic** (применить мгновенно, откат по ошибке — как сейчас) и **non-optimistic** (не трогать состояние, дождаться ответа, применить только на успехе) режимы, выбираемые на уровне конкретной операции, а не домена целиком — так, чтобы новый функционал мог не подключаться к оптимистичному UI вовсе. Идею с независимыми очередями-линиями по домену рассмотрели и отклонили (2026-07-31): ответы бэкенда быстрые (обычно <1с), у пользователя физически нет сценария столкнуть операции двух доменов в этом окне — для личного приложения с одним пользователем это надуманное усложнение. Очередь остаётся единой и строго последовательной глобально.
- **Протокольная идемпотентность, а не точечная.** Каждая операция синка несёт стабильный идентификатор попытки; сервер отличает повтор от нового запроса независимо от типа операции (создание/правка/удаление). Закрывает ограничение по операциям создания/восстановления, явно оставленное вне соседнего плана.
- **Развести две роли соединения к БД.** Производительность (пул на чтение) — отдельно от сериализации бизнес-логики (версия записи/транзакция) — отдельно. После разведения пул на чтение можно расширять не боясь тихо сломать идемпотентность записи.
- **Не маршрутизация, а устранение источника большого сообщения (детали и решение — в бэкенд-документе).** WS-соединение физически сериализовано (один mutex на соединение) — приоритет/роутер не спасает от уже пишущегося большого сообщения. Разбор показал: единственное место, откуда может уйти большое сообщение — досылка метрик после простоя Flatline; сценарий «не открывал приложение сутки» уже закрыт REST-эндпоинтом. Фикс целиком на бэкенде, фронта не касается.
- **Минимальная устойчивость очереди к перезагрузке страницы** — хотя бы для уже отправленных, но не подтверждённых операций, чтобы неудачный момент закрытия вкладки не оставлял клиента и сервер в непримиримом расхождении.

## Область охвата

Переводим на новую архитектуру **дневник еды и деньги** — деньги (транзакции/переводы) уже сегодня используют тот же `SyncQueueService`, что и еда, переделывать логично одновременно. Настройки — отдельный, уже существующий план (`XX-settings-persistence-unification`), сюда не входят и сейчас не трогаются. Версионную модель и общий жизненный цикл синк-операции проектируем так, чтобы настройки могли подключиться позже без пересмотра архитектуры — расширяемость на будущие домены закладывается как требование к дизайну, даже когда сам перевод делается не для всех сразу.

## Не входит в этот план

- Настройки как домен — покрываются отдельным существующим планом, здесь только не мешаем их будущей интеграции.
- Конкретный формат версии (число / etag / vector clock) — решается на этапе имплементации.
- Полный UX конфликтов при «протухшем ретрае поверх более новой правки» — версионирование закрывает техническую часть, разработка UX конфликта — отдельно.
- Персистентная синк-очередь, переживающая перезапуск браузера (не только вкладки) — избыточно для заявленной проблемы.

Бэк — при удалении перевода удалять обе ноги, плюс одноразовый аудит уже осиротевших ног в существующих данных — перенесено в `megaapp-back/plans/16-sqlite-read-write-pool-split._implementation-plan.md`.
